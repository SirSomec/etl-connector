# Дизайн дашборда "Анализ точек"

Дата: 2026-06-01.

## Цель

Добавить в ETL Analytics дашборд "Анализ точек" для оценки стабильности планового заказа по рабочим местам MyGig.

В первой версии стабильность означает регулярность планового спроса: как часто у точки есть заказ в выбранном диапазоне. Основной источник спроса - `mg_orders.amount`.

## Область первой версии

Нужно добавить:

- пункт меню "Анализ точек";
- маршрут `/dashboards/workplace-analysis`;
- фильтры диапазона дат, бренда, города, региона, специальности, типа заказа, контрагента и поиска по точке;
- отображение 12 точек по умолчанию, не меньше 10 одновременно на странице;
- сетку карточек, где одна карточка соответствует одной точке;
- heatmap календарь в стиле GitHub contributions для дневного заказа точки;
- краткие метрики стабильности и объема заказа в каждой карточке;
- пустое состояние, если по фильтрам нет точек с заказами.

Не входит в первую версию:

- произвольный SQL в UI;
- точки без заказов в выбранном диапазоне;
- drill-down до смен, исполнителей или персональных данных;
- экспорт;
- сохраненные фильтры;
- клиентский BI-конструктор или фронтенд-сборка.

## Источники данных

Используются таблицы `mg_*`.

Основные таблицы:

- `mg_orders` - плановые заявки и заказанное количество исполнителей;
- `mg_workplaces` - точки, адреса, город, регион, техническое имя, контрагент;
- `mg_clients` - бренд/клиент;
- `mg_professions` - специальность;
- `mg_contractors` - контрагент.

Связи:

- `mg_orders.workplace = mg_workplaces._id`;
- `mg_orders.client = mg_clients._id`;
- `mg_orders.spec = mg_professions.spec`;
- `mg_workplaces.contractor = mg_contractors._id`.

`mg_jobs` и `mg_job_history` не используются для основной метрики этой версии, потому что пользователь выбрал анализ планового заказа, а не факта выполнения.

## Временная логика

Фильтр периода применяется к `mg_orders.start`.

По умолчанию:

- `from` - первый день текущего месяца;
- `to` - текущая дата;
- `to` включается в пользовательском интерфейсе и передается в ClickHouse как эксклюзивная граница следующего дня.

Заказы с некорректной или пустой датой в `start` не должны попадать в расчет. Удаленные заказы исключаются через `o.deleted = 0`.

## Метрики

Карточка точки показывает:

- название точки: `mg_workplaces.title`, fallback на `technical_name` или `_id`;
- бренд: `mg_clients.title`;
- город и регион: `mg_workplaces.address__city`, `mg_workplaces.address__region`;
- адрес: компактная строка из доступных адресных полей точки;
- `totalOrderedShifts`: `sum(mg_orders.amount)`;
- `activeDays`: количество дней диапазона, где дневная сумма `amount > 0`;
- `rangeDays`: количество календарных дней в выбранном диапазоне;
- `stabilityPercent`: `activeDays / rangeDays * 100`;
- `avgDailyOrder`: `totalOrderedShifts / activeDays`, если `activeDays > 0`;
- дневные значения heatmap: `sum(mg_orders.amount)` по `workplace` и `toDate(mg_orders.start)`.

Цвет ячейки heatmap отражает дневную сумму `mg_orders.amount`:

- нет заказа - нейтральный серый;
- чем выше дневная сумма, тем насыщеннее цвет;
- шкала рассчитывается для текущей выдачи, чтобы 12 карточек были сравнимы между собой.

## Фильтры

Панель фильтров содержит:

- диапазон дат `from/to`;
- клиент/бренд;
- город;
- регион;
- специальность;
- тип заказа `once/regular`;
- контрагент;
- текстовый поиск по названию, техническому имени, городу, региону, улице или адресу точки.

Фильтры клиента/бренда, города, региона, специальности, типа заказа и контрагента должны быть списками выбора значений, доступных в выбранном периоде. Каждый такой фильтр поддерживает выбор одного значения, нескольких значений или отсутствие выбора. Отсутствие выбора означает "все значения".

Списки доступных значений зависят от `from/to` и базовых условий заказов (`o.deleted = 0`, непустая точка, `amount > 0`), но не зависят от уже выбранных значений других фильтров. Это позволяет не скрывать варианты при последовательной настройке фильтрации. Текстовый поиск по точке остается строковым полем, потому что он ищет по нескольким полям точки и не является справочником.

Фильтры должны быть безопасными:

- пользовательские значения передаются как параметры ClickHouse;
- множественные значения передаются как параметры массивов ClickHouse и применяются через `IN {name:Array(String)}`;
- SQL-фрагменты для сортировки и лимита берутся только из whitelist;
- пользовательский произвольный SQL не добавляется.

Для первой версии лимит отображения фиксируется на 12 точках. Если реализация уже естественно поддержит query-параметр `limit`, допустимы только whitelist-значения `10`, `12`, `20`, `50`, по умолчанию `12`.

## Сортировка

Сортировка по умолчанию: `totalOrderedShifts DESC`.

Это соответствует выбранной цели: сначала видеть точки с наибольшим объемом планового заказа.

Допустимые будущие сортировки:

- по объему заказа;
- по индексу стабильности;
- по числу активных дней;
- по названию точки.

В первой реализации достаточно сортировки по объему заказа, если расширение сортировок увеличит объем работ.

## Представление данных

Страница сохраняет спокойный рабочий стиль текущего сервиса.

Структура:

1. Заголовок "Анализ точек".
2. Компактная панель фильтров.
3. Небольшая строка контекста: выбранный период, число дней, правило сортировки.
4. Сетка карточек точек.

Карточка содержит:

- верхнюю строку с названием точки и индексом стабильности;
- подпись с брендом, городом/регионом и адресом;
- компактные метрики: заказано, активные дни, средний дневной заказ;
- календарную heatmap;
- легенду интенсивности.

Для ширины экрана:

- desktop: 3-4 карточки в ряд, если хватает места;
- средняя ширина: 2 карточки;
- mobile: 1 карточка;
- текст должен переноситься без наложений;
- календарь не должен растягивать карточку непредсказуемо.

## Архитектура

Сохраняется текущая архитектура Express + server-rendered HTML без фронтенд-сборки.

Добавляется модуль `src/workplaceAnalysisDashboard.js`, который отвечает за:

- нормализацию фильтров;
- расчет `from`, `toExclusive` и `rangeDays`;
- безопасную сборку условий;
- загрузку доступных значений фильтров за выбранный период;
- загрузку топ-12 точек;
- загрузку дневных значений для выбранных точек;
- объединение результатов в render-ready модель.

`src/server.js` добавляет маршрут `/dashboards/workplace-analysis`.

`src/render.js` добавляет:

- пункт навигации "Анализ точек";
- `renderWorkplaceAnalysisDashboard`;
- helper для карточек;
- helper для heatmap.

## Поток данных

1. Пользователь открывает `/dashboards/workplace-analysis`.
2. Сервер нормализует query-параметры.
3. Первый ClickHouse-запрос загружает справочники фильтров, доступные в выбранном периоде.
4. Сервер оставляет выбранными только значения, которые есть в справочниках периода.
5. Следующий ClickHouse-запрос выбирает топ-12 точек с учетом фильтров и сортировки по `sum(amount) DESC`.
6. Следующий ClickHouse-запрос загружает дневные суммы `amount` только для выбранных `workplace`.
7. Модуль дашборда рассчитывает `stabilityPercent`, `avgDailyOrder`, шкалу heatmap и пустые дни диапазона.
8. Renderer строит серверный HTML.

## Ошибки и пустые состояния

Если по фильтрам нет точек с заказом, страница показывает сообщение:

`Нет точек с заказами за выбранный период.`

Фильтры при этом остаются доступными.

Ошибки ClickHouse рендерятся через существующую страницу ошибки с маскированием секретов.

Дашборд не выводит PII: телефоны, email, ФИО, паспортные данные, ИНН, СНИЛС и данные исполнителей не используются.

## Тестирование

Автоматические тесты должны покрыть:

- нормализацию дат и дефолт текущего месяца;
- расчет `rangeDays`;
- фильтры и защиту от SQL-инъекций;
- безопасный whitelist лимита, если параметр лимита реализован;
- выбор топ-точек и передачу параметров в ClickHouse;
- объединение топ-точек с дневными рядами;
- расчет `stabilityPercent` и `avgDailyOrder`;
- построение пустых дней heatmap внутри диапазона;
- рендер карточек, heatmap, легенды и пустого состояния;
- HTML-экранирование названий точек, брендов, городов и адресов;
- маршрут `/dashboards/workplace-analysis`.

Ручная проверка после реализации:

- `npm test`;
- запуск сервера;
- открытие `/dashboards/workplace-analysis`;
- проверка, что на desktop одновременно видно не менее 10 точек при наличии данных;
- проверка фильтров и отсутствия персональных данных.

## Риски и допущения

- `mg_orders.start` содержит исторические выбросы, поэтому явный диапазон дат обязателен.
- `amount` может быть пустым или нулевым; для heatmap активным днем считается день с суммой `amount > 0`.
- Поиск по адресу зависит от фактического набора адресных полей в `mg_workplaces`; если часть полей отсутствует, поиск должен использовать доступные поля без падения.
- Шкала heatmap в первой версии сравнивает точки внутри текущей выдачи, а не относительно исторического максимума каждой точки.

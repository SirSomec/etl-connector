# Реальный прогресс проверки отчетов

## Цель

Добавить в инструмент `Проверка отчетов` реальный этапный прогресс анализа XLSX-файла, анимацию выполнения и ожидаемое оставшееся время.

Сейчас `/tools/request-report-confirmed-check` работает синхронно: браузер отправляет файл обычной HTML-формой, сервер парсит XLSX, выполняет несколько ClickHouse-поисков и возвращает страницу только после полного завершения. Для больших отчетов пользователь не видит, что именно происходит и сколько еще ждать.

## Область изменений

Входит в первую версию:

- асинхронный запуск проверки отчета из существующего экрана;
- серверный `jobId` и in-memory registry активных задач;
- polling endpoint для статуса задачи;
- реальные этапы прогресса из серверного анализа;
- ETA на основе прошедшего времени и текущего процента;
- анимированный индикатор прогресса в UI;
- сохранение текущего синхронного POST как fallback;
- автоматическая очистка завершенных задач из памяти.

Не входит:

- история проверок;
- запись загруженных XLSX или результатов в `data/`;
- восстановление активной проверки после рестарта процесса;
- произвольный SQL в UI;
- изменение расчетной семантики поиска строк без confirmed-смен.

## Рекомендуемый подход

Использовать in-memory async jobs и polling.

Это минимально меняет текущую архитектуру Express/server-rendered UI, не добавляет зависимостей и не создает новый runtime-файл. Потеря активной задачи при рестарте допустима для первой версии: инструмент интерактивный, а не очередь отчетов с гарантированной доставкой.

Server-Sent Events не выбираются для первой версии, потому что они усложняют авторизацию, обработку разрывов соединения и тесты. SQLite-очередь не выбирается, потому что потребовала бы отдельного дизайна хранения файлов, результатов, TTL и прав на runtime-volume.

## Серверный контракт

Добавить endpoint:

`POST /tools/request-report-confirmed-check/jobs`

Запрос:

- `multipart/form-data`;
- поле `csrfToken`;
- файл `reportFile`;
- лимит размера остается `10 * 1024 * 1024`;
- поддерживаются только `.xlsx`.

Успешный ответ:

```json
{
  "jobId": "request-report-..."
}
```

Ошибки валидации возвращают JSON:

```json
{
  "error": "Выберите XLSX-файл."
}
```

Добавить endpoint:

`GET /tools/request-report-confirmed-check/jobs/:jobId`

Успешный ответ для активной или завершенной задачи:

```json
{
  "jobId": "request-report-...",
  "status": "running",
  "progress": 42,
  "stage": "Поиск confirmed-смен по ID ЛКК",
  "detail": "Батч 3 из 8",
  "estimatedRemainingMs": 18000
}
```

Для завершенной задачи:

```json
{
  "jobId": "request-report-...",
  "status": "done",
  "progress": 100,
  "stage": "Готово",
  "detail": "Проверено 12 430 строк",
  "estimatedRemainingMs": 0,
  "html": "<section>...</section>"
}
```

Для ошибки:

```json
{
  "jobId": "request-report-...",
  "status": "failed",
  "progress": 100,
  "stage": "Ошибка",
  "detail": "Не удалось прочитать XLSX...",
  "estimatedRemainingMs": 0,
  "error": "Не удалось прочитать XLSX..."
}
```

`html` содержит только фрагмент результата или ошибки для вставки в текущую страницу. Полная страница продолжает рендериться существующим `renderRequestReportMissingConfirmedPage`.

## Модель задачи

In-memory registry хранит:

- `id`;
- `status`: `queued`, `running`, `done`, `failed`;
- `createdAt`;
- `updatedAt`;
- `startedAt`;
- `progress`;
- `stage`;
- `detail`;
- `estimatedRemainingMs`;
- `resultHtml`;
- `error`.

Задачи создаются в процессе Node.js. Завершенные и ошибочные задачи удаляются по TTL, например через 15 минут после `updatedAt`. Активные задачи при рестарте теряются; polling для неизвестного `jobId` возвращает `404`.

Файл не сохраняется на диск. Буфер из multipart остается только в памяти до завершения задачи.

## Этапы прогресса

`parseRequestsReportWorkbook` и `findRequestReportRowsWithoutConfirmedShift` получают опциональный `onProgress(event)`.

Минимальные этапы:

1. `queued`: задача создана.
2. `reading-file`: чтение и разбор XLSX.
3. `extracting-rows`: поиск заголовков и извлечение строк отчета.
4. `lookup-external-id`: поиск смен по `mg_orders.external_id` / ID ЛКК.
5. `lookup-composite`: fallback по дате, времени и техническому названию точки.
6. `lookup-employee`: fallback по дате, времени, точке и ФИО исполнителя.
7. `lookup-employee-date`: fallback по дате, точке и ФИО при расхождении времени.
8. `lookup-workplace`: поиск workplace id для CRM-ссылок.
9. `render-result`: сбор результата.
10. `done`: готово.

Процент считается детерминированно по весам этапов и батчам внутри тяжелых ClickHouse lookup-этапов. Если этап не нужен из-за отсутствия кандидатов, он сразу считается завершенным.

Пример весов:

- разбор XLSX: 10%;
- извлечение строк: 10%;
- поиск по ID ЛКК: 25%;
- composite fallback: 15%;
- employee fallback: 15%;
- employee-date fallback: 10%;
- workplace lookup: 10%;
- рендер результата: 5%.

ETA рассчитывается от фактического прошедшего времени:

```text
estimatedRemainingMs = elapsedMs * (100 - progress) / progress
```

До первого ненулевого прогресса ETA показывается как неопределенное ожидание.

## UI

Форма на странице `Проверка отчетов` получает JavaScript-enhancement:

- при отправке кнопка блокируется;
- появляется компактный блок прогресса под формой;
- progress bar плавно анимируется к последнему серверному проценту;
- рядом показываются текущий этап, деталь этапа и ETA;
- после `done` результат вставляется на страницу без полной перезагрузки;
- после `failed` показывается inline-error;
- если `fetch` недоступен или JS отключен, обычный `POST /tools/request-report-confirmed-check` продолжает работать.

Визуальный стиль остается рабочим и спокойным:

- без декоративных hero-блоков;
- прогресс внутри обычного рабочего блока формы;
- текст не должен ломать layout на узком экране;
- анимация только у полосы прогресса и небольшого индикатора активности.

## Безопасность

- Все новые endpoint-ы требуют permission `request-report-matching`.
- `POST /jobs` проверяет CSRF тем же механизмом, что текущий HTML POST.
- Ошибки проходят через существующую санацию.
- XLSX не записывается в репозиторий или `data/`.
- В ответах статуса не возвращаются секреты, query-параметры ClickHouse или содержимое исходного файла.
- `jobId` должен быть случайным и непредсказуемым.

## Совместимость

Существующий маршрут `POST /tools/request-report-confirmed-check` остается рабочим. Это сохраняет поведение без JS и снижает риск регрессии.

Новый JS выбирает асинхронный путь только для формы на странице проверки отчетов. Если асинхронный запуск вернул ошибку сети или невалидный JSON, UI показывает понятную ошибку и предлагает повторить отправку.

## Тестирование

Автоматические тесты:

- `requestReportMissingConfirmed.test.js`: прогресс-callback получает ожидаемые этапы и батч-детали для lookup-функций;
- `render.test.js`: страница содержит элементы прогресса, data-атрибуты для async form, script для polling и fallback form action;
- `server.test.js`: `POST /tools/request-report-confirmed-check/jobs` создает задачу и возвращает `jobId`;
- `server.test.js`: `GET /tools/request-report-confirmed-check/jobs/:jobId` возвращает этапы, завершенный HTML и ошибки;
- `server.test.js`: невалидный файл и пустой upload возвращают JSON-ошибки без запуска задачи;
- `serverAuth.test.js` или существующие auth-тесты: async job endpoint-ы требуют `request-report-matching`.

Ручная проверка:

- открыть `/tools/request-report-confirmed-check`;
- загрузить валидный XLSX и увидеть движение этапов;
- проверить ETA на долгой задаче;
- дождаться результата без перезагрузки страницы;
- проверить ошибку на пустом или не-XLSX файле;
- проверить, что синхронный fallback все еще возвращает результат при обычной отправке формы.

## Риски

- При быстром анализе прогресс может успеть показать только несколько этапов. Это нормально: результат важнее искусственного замедления.
- При рестарте процесса задача потеряется. UI должен показать, что проверка недоступна, и предложить запустить ее заново.
- Долгие ClickHouse-запросы внутри одного батча не дают промежуточного прогресса до возврата запроса. Чтобы прогресс был полезным, тяжелые lookup-и остаются батчированными.

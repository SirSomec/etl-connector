# Дизайн подвкладки "Требуют внимания" в дашборде "Анализ точек"

Дата: 2026-06-04.

## Цель

Расширить дашборд `Анализ точек` отдельной подвкладкой `Требуют внимания`, которая помогает координаторам быстро находить рабочие места, где сейчас нужен ручной фокус для закрытия заказов.

Подвкладка должна ранжировать точки по сочетанию:

- большого незакрытого заказа на ближайшие 7 дней;
- плотности незакрытого заказа по дням;
- наличия рядом базы исполнителей в радиусе 15 км;
- активности этой базы за последние 30 дней.

## Область

Нужно добавить:

- подвкладку внутри маршрута `/dashboards/workplace-analysis`;
- progressive-секцию для тяжелого расчета приоритетов;
- таблицу топ-точек, требующих внимания;
- расчет незакрытого заказа на ближайшие 7 дней;
- расчет общей и активной базы исполнителей по статусам в радиусе 15 км;
- SQL-info для новых метрик;
- тесты нормализации, расчетов, SQL-безопасности, рендера и маршрутов.

Не входит:

- произвольный SQL в UI;
- вывод персональных данных исполнителей;
- фильтрация базы по специальности заказа;
- учет взвешенного влияния по расстоянию;
- карта;
- экспорт;
- пользовательские сохраненные настройки приоритизации.

## Источники данных

Используются таблицы `mg_*` и `appmetrica_sessions`.

Основные таблицы:

- `mg_orders` - плановый заказ, `amount`, `start`, `workplace`, `client`, `spec`, `type`;
- `mg_jobs` - смены, закрывающие заказ через `source = mg_orders._id`;
- `mg_workplaces` - точка, адрес и `location__coordinates`;
- `mg_clients` - бренд;
- `mg_professions` - специальность заказа;
- `mg_contractors` - контрагент точки;
- `mg_workers` - исполнители, статусы и последняя известная геолокация;
- `mg_users` - пользовательская запись исполнителя, нужна для исключения удаленных пользователей;
- `appmetrica_sessions` - активность пользователей в приложении.

## Период

Период подвкладки по умолчанию:

- `attentionFrom` - текущая дата;
- `attentionTo` - текущая дата + 7 дней включительно;
- в ClickHouse `attentionTo` передается как эксклюзивная граница следующего дня.

Подвкладка может использовать существующие фильтры дашборда `Анализ точек`: клиент, город, регион, специальность, тип заказа, контрагент, поиск по точке, include deleted/hidden. При этом календарный период основной вкладки не должен ломать дефолт ближайших 7 дней для подвкладки.

## Незакрытый заказ

Заказ считается незакрытым, если по заявке не хватает смен в закрывающих статусах.

Закрывающие статусы `mg_jobs.status`:

```text
booked, going, inprogress, checkingin, checkingout, completed, delayed, waiting
```

`doccheck` не закрывает заказ, потому что такая смена может быть перехвачена исполнителем с подтвержденными документами.

`completed` закрывает заказ, потому что это успешно завершенная смена.

`confirmed` закрывает заказ только если смена не является нулевым прогулом: есть положительная длительность, начисление/выплата или положительный фактический интервал.

Расчет:

```text
ordered = sum(mg_orders.amount)
covered = count(mg_jobs where deleted = 0 and (status in closing statuses or successful confirmed))
free = greatest(ordered - covered, 0)
```

Расчет должен выполняться на уровне дня и точки, затем агрегироваться до точки за 7 дней.

## Метрики Точки

Для каждой точки в таблице:

- `ordered7d` - суммарный заказ за ближайшие 7 дней;
- `covered7d` - количество смен в закрывающих статусах;
- `free7d` - суммарный незакрытый заказ;
- `coveragePercent` - `covered7d / ordered7d * 100`;
- `maxDailyFree` - максимальный незакрытый заказ в один день;
- `daysWithFree` - количество дней с незакрытым заказом;
- `nearestFreeDate` - ближайший день с незакрытым заказом;
- `totalWorkers15km` - вся база исполнителей с координатами в радиусе 15 км;
- `totalWorkersByStatus15km` - вся база по статусам;
- `activeWorkers30d15km` - активная за последние 30 дней база в радиусе 15 км;
- `activeWorkers30dByStatus15km` - активная база за 30 дней по статусам;
- `activeWorkersPerFreeShift` - `activeWorkers30d15km / free7d`.

База исполнителей:

- радиус только 15 км;
- влияние по расстоянию не учитывать;
- специальность исполнителя не сопоставлять со специальностью заказа;
- активная база - исполнители, чьи `mg_workers.user` встречаются в `appmetrica_sessions.profile_id` за последние 30 дней;
- вся база - исполнители с валидными координатами и не удаленной связанной пользовательской записью.

## Индекс Внимания

Сортировка по умолчанию должна выводить точки, где ручное закрытие наиболее актуально.

Рекомендуемая формула:

```text
attentionScore =
  free7d * 100
  + maxDailyFree * 30
  + daysWithFree * 10
  + startsSoonBoost
  + lowActiveBaseBoost
```

Где:

- `startsSoonBoost = 50`, если `nearestFreeDate` сегодня;
- `startsSoonBoost = 30`, если `nearestFreeDate` завтра;
- `startsSoonBoost = 10`, если `nearestFreeDate` в ближайшие 3 дня;
- `lowActiveBaseBoost = 40`, если `activeWorkersPerFreeShift < 1`;
- `lowActiveBaseBoost = 20`, если `activeWorkersPerFreeShift < 2`;
- иначе `0`.

Формула должна быть реализована как серверный расчет в JS после загрузки агрегатов, чтобы ее можно было менять без переписывания сложного SQL. В SQL допускается сортировать предварительный набор по `free7d DESC, maxDailyFree DESC`.

## UI

Подвкладка размещается внутри `Анализа точек`, например:

- `Обзор точек`;
- `Требуют внимания`.

Вкладки должны быть компактными, без маркетинговых блоков.

Подвкладка `Требуют внимания` показывает:

- краткую строку контекста: период ближайших 7 дней, правило незакрытого заказа, радиус базы 15 км;
- таблицу топ-точек;
- пустое состояние, если нет незакрытого заказа.

Колонки таблицы:

- точка, бренд, город/адрес;
- свободно 7 дней;
- ближайший проблемный день;
- пик дня;
- покрытие;
- вся база 15 км;
- активная база 30 дней 15 км;
- активная база / свободная смена;
- статусы активной базы;
- причина приоритета.

Название точки должно вести в существующую детализацию точки `/dashboards/workplace-analysis/point`.

Причина приоритета строится из главного фактора:

- `много свободного заказа`;
- `пик в ближайшие дни`;
- `мало активной базы`;
- `низкое покрытие`.

Персональные данные исполнителей не выводятся.

## SQL-Набросок

Основной расчет спроса и закрытия:

```sql
WITH filtered_orders AS (
  SELECT
    o._id AS order_id,
    o.workplace AS workplace_id,
    toDate(o.start) AS order_date,
    ifNull(o.amount, 0) AS amount
  FROM mg_orders AS o
  LEFT JOIN mg_workplaces AS w ON o.workplace = w._id
  LEFT JOIN mg_clients AS c ON o.client = c._id
  LEFT JOIN mg_professions AS p ON o.spec = p.spec
  LEFT JOIN mg_contractors AS ct ON w.contractor = ct._id
  WHERE <safe_filters>
),
covered_jobs AS (
  SELECT
    j.source AS order_id,
    count() AS covered
  FROM mg_jobs AS j
  INNER JOIN filtered_orders AS fo ON j.source = fo.order_id
  WHERE ifNull(j.deleted, 0) = 0
    AND (
      ifNull(j.status, '') IN (
        'booked',
        'going',
        'inprogress',
        'checkingin',
        'checkingout',
        'completed',
        'delayed',
        'waiting'
      )
      OR (
        ifNull(j.status, '') = 'confirmed'
        AND (
          ifNull(j.hours, 0) > 0
          OR ifNull(j.payment, 0) > 0
          OR ifNull(j.salary_per_job, 0) > 0
          OR ifNull(j.salary_per_hour, 0) * ifNull(j.hours, 0) > 0
          OR (
            j.start_fact IS NOT NULL
            AND j.finish_fact IS NOT NULL
            AND j.finish_fact > j.start_fact
            AND dateDiff('minute', j.start_fact, j.finish_fact) > 0
          )
        )
      )
    )
  GROUP BY order_id
),
daily_point AS (
  SELECT
    fo.workplace_id,
    fo.order_date,
    sum(fo.amount) AS ordered,
    sum(ifNull(cj.covered, 0)) AS covered,
    greatest(sum(fo.amount) - sum(ifNull(cj.covered, 0)), 0) AS free
  FROM filtered_orders AS fo
  LEFT JOIN covered_jobs AS cj ON fo.order_id = cj.order_id
  GROUP BY fo.workplace_id, fo.order_date
)
SELECT ...
```

Расчет базы 15 км должен переиспользовать подход из `heatmapDashboard.js`: сначала выбрать точки с незакрытым заказом и валидными координатами, затем подобрать исполнителей в bounding box и отфильтровать `greatCircleDistance(...) <= 15000`.

## Кеширование

Если расчет базы 15 км окажется дорогим, добавить файловый кеш в `data/`.

Требования:

- не коммитить runtime-файл;
- писать атомарно через существующий helper;
- не использовать общий временный путь вида `cache.json.tmp`;
- добавить тест на сохранение свежих значений и устаревание;
- если новый кеш пишет один файл из параллельных запросов, добавить тест конкурентной записи или использовать уже протестированную атомарную запись.

## Ошибки И Безопасность

- Все пользовательские значения передавать параметрами ClickHouse.
- Сортировки, лимиты и секции брать только из whitelist.
- Не выводить PII.
- Ошибки ClickHouse рендерить через существующий механизм маскирования.
- Не добавлять произвольный SQL в UI.

## Тестирование

Автоматические тесты:

- нормализация активной подвкладки;
- период ближайших 7 дней;
- расчет `free7d`, `covered7d`, `coveragePercent`;
- `completed` закрывает заказ;
- `doccheck`, `cancelled`, `failed`, `expired`, `toolate` не закрывают заказ;
- расчет базы 15 км без весов;
- раздельный расчет всей базы и активной базы за 30 дней по статусам;
- `attentionScore` и причина приоритета;
- SQL не содержит пользовательских значений напрямую;
- route `/dashboards/workplace-analysis/section?section=attention`;
- рендер подвкладок и таблицы attention;
- пустое состояние.

Ручная проверка:

- открыть `/dashboards/workplace-analysis`;
- переключиться на подвкладку `Требуют внимания`;
- убедиться, что таблица показывает топ-точки с незакрытым заказом;
- проверить ссылку в детализацию точки;
- проверить отсутствие телефонов, email, ФИО и других PII.

В каждом файле зафиксированы фактические SQL-шаблоны из `src/*Dashboard.js`, параметры фильтров, метрики и логика их расчета.

## Соглашения

Обозначения вида `<whereSql>`, `<filtered_orders>` или `<revenue_expression>` используются только для динамических фрагментов SQL, которые в коде собираются отдельно и описаны в том же документе. Параметры ClickHouse оставлены в форме `{name:Type}`, как они передаются из приложения.

## Обязательное правило для новых расчетных блоков

Каждый новый KPI, отдельное числовое значение, строка/ячейка расчетной таблицы, график, карта, календарь, heatmap или другой графический вывод данных должен иметь SQL-info metadata: стабильный `id`, краткое описание для пользователя и SQL-шаблон с ClickHouse-параметрами. Видимость SQL контролируется общим правом `SQL метрик`.

Для каждого отображаемого значения нужен явный `metricId` в `src/sqlMetricInfo.js`. Запрещено наследовать SQL родительской панели или показывать упрощенный запрос, если метрика считается другим SQL-шаблоном. Если блок использует несколько запросов, SQL-info должен показывать эти запросы или явно описанный общий шаблон без потери смысла. Тесты должны проверять, что новые `metricId` имеют собственную metadata и что неизвестный дочерний `metricId` не получает чужой SQL.

Исключение допустимо только для статического UI и preview сырых строк таблицы. Если новый блок выводит агрегированные данные или визуализирует расчет, metadata и тест на видимость по праву `sql-inspector` добавляются вместе с блоком.

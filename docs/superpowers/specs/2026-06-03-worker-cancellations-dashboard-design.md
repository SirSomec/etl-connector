# Дизайн дашборда "Отмены гигерами"

Дата: 2026-06-03.

## Цель

Добавить в ETL Analytics дашборд для анализа отмен смен со стороны исполнителей. Экран должен помогать аналитикам находить гигеров с рисковым поведением: отмены по инициативе исполнителя, поздние отмены менее чем за 24 часа до старта, отмены после планового старта смены и отдельные провалы `failed`.

## Область первой версии

В первой версии нужно:

- добавить пункт меню `Отмены гигерами`;
- добавить маршрут `/dashboards/worker-cancellations`;
- добавить секционный маршрут `/dashboards/worker-cancellations/section`;
- показать фильтр диапазона дат по плановому старту смены `mg_jobs.start`;
- показать настройку количества строк на странице;
- показать таблицу исполнителей с серверной сортировкой по кликабельным заголовкам;
- добавить пагинацию;
- не добавлять пользовательский произвольный SQL;
- выводить полный номер телефона, потому что это явно требуется для операционной работы.

Не входит в первую версию:

- графики и KPI-карточки;
- экспорт в CSV или Excel;
- drill-down до отдельных смен;
- фильтры по клиентам, городам, специальностям или статусам исполнителя;
- маскирование телефона.

## Архитектура

Дашборд следует текущему серверному паттерну проекта:

1. Основной маршрут `/dashboards/worker-cancellations` нормализует фильтры и рендерит легкий shell: заголовок, форму фильтров, подпись расчета и заглушку таблицы.
2. Секционный маршрут `/dashboards/worker-cancellations/section?section=workers` выполняет расчет таблицы и возвращает HTML-фрагмент без полного layout.
3. Секция использует общий `dashboardSectionCache` с TTL 10 часов. Ключ кеша включает диапазон дат, сортировку, направление сортировки, номер страницы и размер страницы.
4. Ошибки секции рендерятся локальным фрагментом ошибки и проходят через существующую маскировку секретов.

Для дашборда добавляется отдельный модуль, например `src/workerCancellationsDashboard.js`, по аналогии с существующими dashboard-модулями. Рендеринг добавляется в `src/render.js`, маршруты и активная навигация - в `src/server.js`.

## Доступ и навигация

Добавляется permission id `worker-cancellations`.

В `PERMISSION_DEFINITIONS` появляется пункт:

- label: `Отмены гигерами`;
- description: просмотр таблицы исполнителей с отменами, поздними отменами и провалами смен.

Администратор получает доступ автоматически через текущую роль `admin`. Для аналитиков доступ управляется так же, как для других дашбордов.

## Источники данных

Используются таблицы слоя `mg_*`:

- `mg_jobs` - базовая таблица смен, статус и плановый старт;
- `mg_job_history` - события отмены, инициатор и время события;
- `mg_workers` - исполнитель и город;
- `mg_users` - ФИО и телефон учетной записи исполнителя.

Связи:

- `mg_jobs.worker = mg_workers._id`;
- `mg_workers.user = mg_users._id`;
- `mg_job_history.job = mg_jobs._id`.

`mg_job_history` используется только через join к уже отфильтрованным сменам периода, чтобы не считать период по истории и не задваивать смены.

## Временная логика

Все метрики считаются по выбранному диапазону планового старта смены:

- `j.start >= {from:DateTime}`;
- `j.start < {to:DateTime}`, где `to` - день после выбранной даты `По`.

В UI поле `По` работает включительно. В технической подписи указывается: `Период по плановому старту смены`.

Метрика "после старта" сравнивается только с плановым `mg_jobs.start`, а не с `start_fact`.

## Базовая выборка исполнителей

В таблицу попадают все исполнители, у которых есть хотя бы одна смена `mg_jobs` в выбранном диапазоне `mg_jobs.start`, независимо от статуса смены. Это значит, что строки с нулевыми отменами остаются в результате, если у исполнителя были любые смены за период.

Смены без `worker` не попадают в таблицу, потому что их невозможно связать с конкретным исполнителем.

## Колонки таблицы

Таблица содержит:

- `ФИО`;
- `Телефон`;
- `Город`;
- `Выполнено`;
- `Отмены worker`;
- `Отмены worker < 24ч`;
- `Отмены после старта`;
- `Провалы / failed`.

ФИО собирается из доступных полей `mg_users`: фамилия и имя обязательны для отображения при наличии, отчество добавляется только если соответствующее поле существует в фактической схеме. Если ФИО пустое, fallback - `worker_id`.

Телефон выводится полностью из `mg_users.phone`.

Город берется из городского или адресного поля `mg_workers`. При реализации нужно проверить фактическую схему `mg_workers` и использовать наиболее типизированное city-поле; если город пустой, выводится пустая строка.

## Метрики

### Выполнено

Количество уникальных смен исполнителя в выбранном периоде, где:

```sql
mg_jobs.status = 'confirmed'
AND <successful_confirmed_shift_condition>
```

Нулевой прогул - это `confirmed`-смена с длительностью `0:00` и нулевым начислением/выплатой. Такие смены не входят в метрику "Выполнено".

### Отмены worker

Количество уникальных смен исполнителя в выбранном периоде, где текущий статус смены:

```sql
mg_jobs.status = 'cancelled'
```

и в `mg_job_history` есть событие этой смены с:

```sql
status = 'cancelled'
initiator = 'worker'
```

Если по одной смене есть несколько таких событий, смена считается один раз.

### Отмены worker < 24ч

Подмножество `Отмены worker`: событие отмены по инициативе исполнителя произошло менее чем за 24 часа до планового старта смены:

```sql
cancelled_at >= mg_jobs.start - INTERVAL 24 HOUR
AND cancelled_at < mg_jobs.start
```

`cancelled_at` берется как `coalesce(mg_job_history.createdAt, mg_job_history.updatedAt)`.

### Отмены после старта

Количество уникальных отмененных смен исполнителя в выбранном периоде, где текущий статус смены:

```sql
mg_jobs.status = 'cancelled'
```

и любое событие отмены в истории произошло после или в момент планового старта:

```sql
cancelled_at >= mg_jobs.start
```

Инициатор не ограничивается.

### Провалы / failed

Отдельный счетчик уникальных смен исполнителя в выбранном периоде, где:

```sql
mg_jobs.status = 'failed'
```

`failed` не включается в метрики отмен и показывается соседним столбцом.

## Сортировка

Все заголовки таблицы кликабельные. Сортировка выполняется на сервере и применяется ко всему результату, а не только к текущей странице.

Поддерживаются только whitelisted sort keys:

- `fullName`;
- `phone`;
- `city`;
- `confirmedShifts`;
- `workerCancellations`;
- `workerCancellations24h`;
- `postStartCancellations`;
- `failedShifts`.

Пользовательские значения сортировки не вставляются в SQL напрямую. Реализация выбирает выражение `ORDER BY` из whitelist.

Поведение:

- первый клик по числовой колонке сортирует по убыванию;
- первый клик по текстовой колонке сортирует по возрастанию;
- повторный клик по текущей колонке переключает направление;
- текущая сортировка отмечается стрелкой в заголовке;
- сортировка по умолчанию: `workerCancellations24h DESC`, затем `workerCancellations DESC`, затем `failedShifts DESC`, затем ФИО.

## Пагинация

Таблица использует серверную пагинацию.

Размер страницы выбирается в UI:

- 50;
- 100;
- 200;
- 500.

Значение по умолчанию - 100. Любое другое значение нормализуется к 100.

Пагинация сохраняет:

- диапазон дат;
- sort key;
- направление сортировки;
- размер страницы.

Для корректного отображения количества страниц секция должна вернуть общее количество исполнителей в базовой выборке. Первая версия использует отдельный `COUNT`-запрос по той же агрегированной выборке без `ORDER BY`, `LIMIT` и `OFFSET`; это проще тестировать и не связывает пагинацию с поддержкой оконных функций.

## UI

Экран остается плотным рабочим инструментом:

- заголовок `Отмены гигерами`;
- техническая подпись с диапазоном и правилом периода;
- компактная `filter-bar`;
- заглушка `Загружается` до ответа секции;
- таблица с горизонтальным скроллом на узких экранах;
- пагинация под таблицей;
- пустое состояние `Нет исполнителей со сменами за выбранный период`.

В таблице числовые колонки выравниваются вправо. Текстовые значения экранируются через существующий HTML escaping.

## Безопасность

Произвольный SQL в UI не добавляется. Все пользовательские значения дат, страницы и размера страницы нормализуются перед запросом. Сортировка выбирается только из whitelist.

Дашборд намеренно выводит PII: ФИО и полный телефон исполнителя. Это исключение принято для операционной задачи анализа отмен. Остальные персональные поля, включая email, паспортные данные, ИНН и СНИЛС, не выводятся.

Ошибки ClickHouse не должны раскрывать пароли, токены или значения секретов.

## Тестирование

Автоматические тесты должны покрыть:

- нормализацию дат, страницы, размера страницы, sort key и направления;
- fallback для некорректных фильтров;
- построение SQL без пользовательского `ORDER BY`;
- расчет маппинга строк из ClickHouse в модель таблицы;
- отдельность `cancelled` и `failed`;
- условия `initiator = 'worker'`;
- условие `< 24ч` до планового старта;
- условие отмены после планового старта;
- shell-маршрут без тяжелого запроса;
- section-маршрут с кешированием;
- рендер таблицы, сортируемых заголовков, пагинации и пустого состояния;
- экранирование ФИО, телефона, города и fallback-значений;
- активную навигацию и permission id.

Ручная проверка:

- `npm test`;
- открыть `/dashboards/worker-cancellations`;
- применить разные диапазоны дат;
- проверить смену сортировки кликом по заголовкам;
- проверить размеры страницы 50, 100, 200, 500;
- проверить переходы между страницами;
- убедиться, что телефон выводится полностью;
- убедиться, что ошибки секций не ломают весь экран.

## Риски

- Точная колонка города в `mg_workers` может отличаться от ожидаемой. Перед реализацией нужно запросить фактическую схему таблицы и выбрать лучшее city-поле.
- `mg_job_history` может содержать несколько событий отмены на одну смену. Метрики должны использовать уникальные `job_id`, а не число строк истории.
- `coalesce(createdAt, updatedAt)` может быть пустым для отдельных исторических событий. Такие события не участвуют в метриках `< 24ч` и `после старта`, но могут подтверждать сам факт `Отмены worker`, если есть `status = 'cancelled'` и `initiator = 'worker'`.
- Большие диапазоны могут быть тяжелыми из-за агрегации по `mg_jobs` и `mg_job_history`. Секционная загрузка, пагинация и кеш уменьшают пользовательское ожидание, но не отменяют стоимость холодного запроса.

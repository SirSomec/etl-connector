# Дизайн дашборда "Продажи по проектам"

Дата: 2026-06-01.

## Цель

Добавить в ETL Analytics первый аналитический дашборд для данных MyGig: "Продажи по проектам". Дашборд показывает динамику выполнения заявок клиентов по брендам, периодам, статусам работ и гигерам.

В этом дашборде "проект" означает бренд клиента: `mg_clients.title`.

## Область первой версии

В первой версии нужно:

- добавить левое боковое меню как постоянную навигацию приложения;
- оставить существующий просмотр таблиц доступным через пункт меню "Таблицы";
- добавить пункт меню "Продажи по проектам";
- добавить маршрут `/dashboards/sales-by-project`;
- показать фильтры периода: день, неделя, месяц, квартал;
- показать фильтр диапазона дат;
- показать KPI по выбранному диапазону;
- показать динамику по периодам;
- показать детализацию по брендам;
- показать детализацию статусов работ;
- не добавлять произвольный SQL в UI.

Интерфейс остается серверно-рендеренным HTML без фронтенд-сборки. Это соответствует текущей архитектуре сервиса и достаточно для первой итерации.

## Источники данных

По умолчанию используются таблицы `mg_*`.

Основные таблицы:

- `mg_orders` - плановые заявки клиентов и заказанное количество смен;
- `mg_job_history` - актуальная история смен, статусов, исполнителей и инициаторов бронирования;
- `mg_clients` - бренды клиентов;
- `mg_workplaces` - ТТ и адресная детализация;
- `mg_contractors` - тип договора и комиссия заказчика для SaaS;
- `mg_transactions` - доплаты к сменам, если они связаны со сменой через `entityId`.

`mg_jobs` не является основным источником для этого дашборда, потому что в текущем ETL она может быть менее свежей, чем `mg_job_history`. Ее можно использовать позднее как контрольный источник, если появится расхождение в статусах.

## Временная логика

Основной период дашборда строится по плановой дате смены/заявки:

- для заказов: `mg_orders.start`;
- для смен из истории: `parseDateTimeBestEffortOrNull(mg_job_history.start)`.

Периодизация:

- день: `toDate(start)`;
- неделя: `toStartOfWeek(start)`;
- месяц: `toStartOfMonth(start)`;
- квартал: `toStartOfQuarter(start)`.

Диапазон дат применяется одинаково к заказам и сменам. Значения с пустой или нераспарсенной датой исключаются из расчетов.

## Модель смен

Для расчетов по сменам используется нормализованный слой запроса "одна смена = одна строка":

- базовый факт за актуальные периоды берется из `mg_jobs`, а `mg_job_history` используется для событий самоброни;
- поля бренда, ТТ, исполнителя, заказа, ставок и часов берутся из последнего актуального состояния смены;
- признак самоброни берется из события бронирования этой смены, где `status = 'booked'` и `initiator = 'worker'`.

Такой слой нужен, чтобы не задвоить смены из-за нескольких строк истории.

## Метрики

### Заказано смен

`sum(mg_orders.amount)` по заказам в выбранном периоде.

Удаленные заказы исключаются: `deleted = 0`.

### Отработано смен

Количество уникальных смен с успешным `mg_jobs.status = 'confirmed'`. `confirmed`-смены с длительностью `0:00` и нулевым начислением/выплатой считаются прогулом и не участвуют в показателе.

### SLA, %

`Отработано смен / Заказано смен * 100`.

Если заказанных смен нет, SLA показывается как `0`.

### Выручка, руб.

Выручка считается только по подтвержденным сменам.

Для `contract_type = 'saas'`:

`ставка гигера за смену + комиссия заказчика за смену + доплаты заказчика`.

В первой версии:

- ставка гигера за смену = `salary_per_job`, если заполнено;
- если `salary_per_job` пустой, ставка гигера за смену = `salary_per_hour * hours`;
- комиссия заказчика = ставка гигера за смену * `mg_contractors.comission / 100`;
- `mg_contractors` связывается через ТТ: `mg_workplaces.contractor = mg_contractors._id`.

Для `contract_type = 'services'`:

`ставка заказчика за смену + доплаты заказчика`.

В первой версии:

- ставка заказчика за смену = `payment_per_job`, если заполнено;
- если `payment_per_job` пустой, ставка заказчика за смену = `payment_per_hour * hours`.

Для остальных или пустых типов договора используется логика `services`, потому что она опирается на клиентскую ставку.

Доплаты заказчика:

- берутся из `mg_transactions`;
- фильтр: `transaction_type = 'surcharge'`;
- связь со сменой: `mg_transactions.entityId = job`;
- сумма: `coalesce(nullIf(payment_amount, 0), amount, 0)`.

Это допущение нужно проверить на следующих итерациях с бизнесом, потому что в ETL нет отдельного очевидного поля "сумма заказчика за доплату".

### Уникальные исполнители

`countDistinct(worker)` среди подтвержденных смен.

### Количество ТТ с заказами

`countDistinct(mg_orders.workplace)` по заказам с `amount > 0`.

### Количество ТТ с выполненными сменами

`countDistinct(workplace)` среди подтвержденных смен.

### Отмены

Количество уникальных смен, у которых последний известный статус равен `cancelled`.

### % самоброней

`подтвержденные смены с booked-событием initiator = 'worker' / подтвержденные смены * 100`.

Если подтвержденных смен нет, показатель показывается как `0`.

### Средняя ставка гигеру в час

`avgIf(mg_orders.salary_per_hour, mg_orders.salary_per_hour > 0)`.

Это соответствует формулировке "сумма ставок гигера за час из всех заказов, деленная на количество всех заказов". В первой версии показатель считается по заказам, а не по фактическим сменам.

## Представление данных

Страница дашборда содержит:

- заголовок "Продажи по проектам";
- компактную панель фильтров: периодизация, дата с, дата по;
- KPI-блок с основными метриками;
- таблицу динамики по периодам;
- простую визуализацию динамики SLA и отработанных смен;
- таблицу брендов с теми же ключевыми метриками;
- таблицу статусов работ;
- техническую подпись с выбранными правилами расчета.

Визуализация должна быть простой и устойчивой: HTML/CSS или inline SVG без внешней JS-библиотеки.

## Навигация

Общий layout получает левое меню:

- `Таблицы` ведет на `/`;
- `Продажи по проектам` ведет на `/dashboards/sales-by-project`.

На странице выбранный пункт подсвечивается. На мобильной ширине меню становится верхним компактным блоком, чтобы не перекрывать таблицы и фильтры.

## Ошибки и пустые состояния

Если ClickHouse возвращает ошибку, используется существующая страница ошибки с маскированием секрета.

Если по фильтрам нет данных, дашборд показывает пустое состояние без падения:

- KPI равны нулю;
- таблицы показывают сообщение "Нет данных за выбранный период";
- фильтры остаются доступными.

## Тестирование

Автоматические тесты должны покрыть:

- новый маршрут `/dashboards/sales-by-project`;
- рендер бокового меню и активного пункта;
- рендер KPI и таблиц дашборда;
- экранирование брендов, статусов и текстовых значений;
- построение ClickHouse-запросов без произвольного SQL из пользовательского ввода;
- валидацию периода агрегации: `day`, `week`, `month`, `quarter`;
- корректную обработку пустых результатов.

Ручная проверка:

- контейнер собирается;
- `npm test` проходит;
- дашборд открывается в браузере на `http://localhost:3000/dashboards/sales-by-project`;
- меню работает на страницах таблиц и дашборда;
- метрики не раскрывают персональные данные гигеров.

## Не входит в первую версию

- авторизация;
- сохраненные фильтры;
- экспорт в Excel/CSV;
- произвольный SQL;
- drill-down до персональных данных исполнителя;
- полноценная BI-визуализация с клиентским state management.

# Дизайн дашборда "Движение по воронке исполнителей"

Дата: 2026-06-15.

## Цель

Добавить в ETL Analytics дашборд для анализа движения пользователей-исполнителей по воронке MyGig. Экран должен помогать аналитикам видеть, сколько пользователей проходит ключевые стадии, где происходят потери, как меняются переходы во времени и какие сегменты дают лучшие или худшие конверсии.

## Область первой версии

В первой версии нужно:

- добавить пункт меню `Воронка исполнителей`;
- добавить маршрут `/dashboards/worker-funnel`;
- добавить секционный маршрут `/dashboards/worker-funnel/section` для тяжелых расчетных блоков;
- поддержать два режима периода: `Когорта регистраций` и `События в периоде`;
- показать фильтры периода, источника, города, устройства, текущего статуса исполнителя и специальности;
- показать KPI по размеру выборки, достижению `ready`, первой брони и первой успешной смены;
- показать линейную воронку переходов между стадиями с количеством, конверсией, потерями и медианным временем перехода;
- показать динамику переходов по дням или неделям;
- показать таблицу сегментов по источникам, городам и устройствам;
- показать блок узких мест: самый большой абсолютный отвал, самая низкая конверсия, самый долгий медианный переход;
- не выводить персональные данные конкретных пользователей;
- не добавлять пользовательский произвольный SQL.

Не входит в первую версию:

- список конкретных пользователей в стадии или сегменте;
- экспорт в CSV или Excel;
- редактирование статусов или комментариев;
- прогноз переходов;
- маркетинговая атрибуция по AppMetrica;
- произвольный конструктор стадий.

## Аналитическая модель

Дашборд строится только по пользователям-исполнителям. Работодатели, операторы, администраторы и другие роли не входят в расчет.

Базовая последовательность стадий:

```text
Регистрация -> Профиль исполнителя -> Документы загружены -> Ready -> Первая бронь -> Первая успешная смена
```

Стадии считаются по первым датам событий:

- `Регистрация`: `mg_users.createdAt`;
- `Профиль исполнителя`: `mg_workers.createdAt`;
- `Документы загружены`: `parseDateTime64BestEffortOrNull(nullIf(mg_workers.first_passport_upload, 'NaT'))`;
- `Ready`: `parseDateTime64BestEffortOrNull(nullIf(mg_workers.first_ready_status, 'NaT'))`;
- `Первая бронь`: первое событие `mg_job_history` со статусом `booked`;
- `Первая успешная смена`: первая успешная `confirmed` смена без признака прогула.

`mg_workers.status` используется как текущий статус и фильтр, а не как история переходов. Полного журнала изменения статуса исполнителя в подтвержденной схеме нет, поэтому первая версия не заявляет точную историю всех смен статусов `lead -> registred -> moderation -> uploaded -> ready -> booked -> worked`.

## Режимы периода

### Когорта регистраций

В выборку входят пользователи, у которых:

```sql
mg_users.createdAt >= {from:DateTime}
AND mg_users.createdAt < {to:DateTime}
```

UI-поле `По` работает включительно, технически `to` передается как следующий день после выбранной даты. В этом режиме дашборд отвечает на вопрос: "Что произошло с пользователями, зарегистрированными в выбранный период?"

Для каждой стадии считается, сколько пользователей из когорты когда-либо дошли до этой стадии. Даты стадий могут быть позже выбранного периода.

### События в периоде

В выборку перехода входят пользователи, у которых дата целевой стадии попала в период:

```sql
stage_at >= {from:DateTime}
AND stage_at < {to:DateTime}
```

В этом режиме дашборд отвечает на вопрос: "Какие переходы случились в выбранный период?" Один пользователь может участвовать в нескольких переходах, если несколько его milestone-событий попали в период.

## Источники данных

Используются таблицы слоя `mg_*`:

- `mg_users` - пользовательская регистрация, роль, источник, устройство;
- `mg_workers` - профиль исполнителя, текущий статус, город, специальность, milestone-даты документов и `ready`;
- `mg_jobs` - успешные смены, плановые и фактические даты;
- `mg_job_history` - события первой брони;
- `mg_professions` - подписи специальностей.

Связи:

- `mg_workers.user = mg_users._id`;
- `mg_jobs.worker = mg_workers._id`;
- `mg_job_history.job = mg_jobs._id`;
- `mg_workers.spec = mg_professions.spec`.

`mygig_*` не используется. AppMetrica не входит в первую версию, потому что этот дашборд анализирует платформенную воронку исполнителя, а не мобильную атрибуцию установок.

## Метрики

### Количество на стадии

Количество уникальных пользователей-исполнителей, у которых заполнена дата соответствующей стадии и пользователь проходит фильтры.

Единица учета - `mg_users._id`, если он заполнен; строки `mg_workers` без связанного пользователя не входят в пользовательскую воронку.

### Конверсия перехода

Для перехода `A -> B`:

```text
users_at_B / users_at_A * 100
```

В когортном режиме обе величины считаются внутри одной регистрационной когорты. В событийном режиме конверсия считается для событий целевой стадии в периоде относительно событий предыдущей стадии в периоде; подпись в UI явно указывает, что это операционный event-rate, а не когортная конверсия.

### Потери

Для перехода `A -> B`:

```text
users_at_A - users_at_B
```

Если в событийном режиме целевая стадия больше предыдущей из-за исторического хвоста, потери показываются как `0`, а рядом выводится подпись `поток стадий несинхронен по датам`. Это защищает UI от отрицательных "потерь", которые вводят в заблуждение.

### Медианное время перехода

Для перехода `A -> B`:

```text
median(dateDiff('hour', stage_a_at, stage_b_at)) / 24
```

В расчет входят только пользователи, у которых обе даты заполнены и `stage_b_at >= stage_a_at`. Отрицательные или неполные интервалы не участвуют.

### Первая успешная смена

Используется существующее доменное правило успешной `confirmed` смены без признака прогула:

- `status = 'confirmed'`;
- и есть положительный признак факта: часы, оплата, начисление, ставка на часы или валидный интервал `start_fact < finish_fact`.

При реализации нужно переиспользовать общий helper/SQL из `src/successfulConfirmedShift.js` или соответствующий общий SQL-модуль, чтобы не расходиться с существующими дашбордами.

### Первая бронь

Первая бронь считается по истории смен:

```sql
mg_job_history.status = 'booked'
AND ifNull(mg_job_history.worker, '') != ''
```

Дата события берется как:

```sql
coalesce(mg_job_history.createdAt, mg_job_history.updatedAt)
```

Событие связывается с исполнителем через `mg_job_history.worker = mg_workers._id`. Текущий `mg_jobs.status = 'booked'` не используется для первой брони, потому что это снимок текущего состояния смены и он не показывает исторический факт бронирования у пользователей, которые уже дошли до следующих стадий.

## Фильтры

Поддерживаются:

- `from`, `to` - включительный диапазон дат в UI;
- `mode` - `cohort` или `events`;
- `source` - источник привлечения;
- `city` - город исполнителя;
- `device` - устройство;
- `workerStatus` - текущий статус исполнителя;
- `profession` - специальность.

Источник привлечения:

- основной источник: `mg_users.meta__source`, если не пустой и не `NULL`;
- fallback: `mg_users.reg_source`;
- пустые значения группируются как `Не указан`.

Город:

- основной источник: `mg_workers.full_address__city`;
- пустые значения группируются как `Не указан`.

Устройство:

- источник: `mg_users.smartphone_type`;
- пустые значения группируются как `Не указано`.

Специальность:

- фильтр хранит технический `spec`;
- подпись берется из `mg_professions.caption`, если найдена, иначе используется сам `spec`.

## UI

Экран остается плотным рабочим инструментом для аналитика.

Структура:

1. Заголовок `Воронка исполнителей`.
2. Техническая подпись с режимом, периодом и правилом расчета.
3. Компактная панель фильтров.
4. KPI-строка:
   - размер выборки;
   - дошли до `ready`;
   - дошли до первой брони;
   - дошли до первой успешной смены.
5. Основной блок переходов:
   - стадия;
   - пользователей на стадии;
   - конверсия к предыдущей стадии;
   - потери;
   - медианное время перехода.
6. Динамика переходов по дням или неделям.
7. Таблица сегментов.
8. Блок узких мест.

Для desktop основной блок и динамика показываются в двух колонках. Для мобильного экрана порядок линейный:

```text
фильтры -> KPI -> переходы -> динамика -> сегменты -> узкие места
```

Все ключевые значения видны без hover. Hover может давать подсказки, но не является единственным способом прочитать данные.

## Визуализация

Основная визуализация - линейная воронка переходов с горизонтальными полосами. Для каждого перехода:

- длина полосы кодирует количество пользователей на стадии;
- рядом явно подписаны количество, процент перехода и потери;
- медианное время перехода показывается отдельным числом;
- проблемные переходы подсвечиваются только если они являются минимумом по конверсии или максимумом по потере/времени.

Динамика - компактный временной график по выбранному переходу или по всем переходам малыми рядами. В первой версии достаточно серверно-рендеренного HTML/SVG или CSS-графика в стиле существующих дашбордов; WebGL, canvas и декоративная анимация не нужны.

Цветовые роли:

- нейтральный фон и сетка;
- один основной акцент для выбранного режима/перехода;
- отдельный спокойный предупреждающий цвет для узкого места;
- цвет не должен быть единственным носителем смысла: числа и подписи обязательны.

## Сегменты

Сегментная таблица показывает вклад и качество переходов по измерениям:

- источник;
- город;
- устройство.

В первой версии таблица может иметь переключатель измерения или отдельные вкладки. Для каждого сегмента показываются:

- значение сегмента;
- пользователей на входной стадии;
- пользователей на конечной стадии;
- конверсия до `ready`;
- конверсия до первой брони;
- конверсия до первой успешной смены;
- медианное время до `ready`;
- медианное время до первой успешной смены.

Сегменты с малой базой помечаются как малые выборки. Порог первой версии - меньше 30 пользователей на входной стадии.

## Архитектура

Добавляется отдельный dashboard-модуль:

- `src/workerFunnelDashboard.js` - нормализация фильтров, SQL, загрузка данных, merge-модель;
- `src/render.js` - shell, секции и HTML-фрагменты;
- `src/server.js` - маршруты, права, активная навигация;
- `src/sqlMetricInfo.js` - описания KPI и ключевых SQL-метрик;
- `docs/dashboards/worker-funnel.md` - пользовательская и SQL-документация.

Маршруты:

- `GET /dashboards/worker-funnel` - легкий shell;
- `GET /dashboards/worker-funnel/section?section=summary` - KPI, переходы и узкие места;
- `GET /dashboards/worker-funnel/section?section=dynamics` - динамика;
- `GET /dashboards/worker-funnel/section?section=segments` - сегменты.

Секции можно объединить при реализации, если тесты покажут, что запросы достаточно быстрые. Публичный UI не должен зависеть от этого внутреннего решения.

## Доступ и навигация

Добавляется permission id `worker-funnel`.

В `PERMISSION_DEFINITIONS` появляется пункт:

- label: `Воронка исполнителей`;
- description: просмотр агрегированной воронки переходов пользователей-исполнителей.

Администратор получает доступ автоматически через текущую роль `admin`. Для аналитиков доступ управляется так же, как для других дашбордов.

## Производительность и кеширование

Основной расчет строит milestone-набор на уровне пользователя/исполнителя и агрегирует его в ClickHouse до передачи в Node.js. В Node.js не нужно загружать список всех пользователей.

По умолчанию период - последние 30 дней. Пользователь может выбрать другой диапазон, но большие периоды могут выполняться дольше.

Секционные ответы могут использовать существующий `dashboardSectionCache`. Ключ кеша должен включать:

- версию расчета;
- section;
- режим;
- период;
- все фильтры;
- выбранное измерение сегмента, если применимо.

Кеш хранится в `data/` и остается runtime-состоянием деплоя.

## Ошибки и пустые состояния

Если выбранная комбинация фильтров не дает данных, экран показывает пустое состояние:

```text
Нет пользователей-исполнителей для выбранных фильтров.
```

Если одна секция упала, shell и остальные секции остаются доступными, а проблемная секция показывает локальный фрагмент ошибки через существующую маскировку секретов.

Если в событийном режиме переходы несинхронны по датам и дают неинтуитивные сравнения, UI показывает пояснение рядом с метриками потерь.

## Безопасность

Произвольный SQL в UI не добавляется. Все фильтры нормализуются и передаются в ClickHouse параметрами.

Дашборд не выводит:

- телефон;
- email;
- ФИО;
- паспортные данные;
- ИНН;
- СНИЛС;
- конкретные `user_id` и `worker_id` в таблицах.

Показываются только агрегаты и сегменты. Если позже понадобится drill-down до конкретных пользователей, это отдельный согласованный дизайн с маскированием и проверкой прав.

## Тестирование

Автоматические тесты должны покрыть:

- нормализацию режима, дат и фильтров;
- fallback для некорректных фильтров;
- построение SQL только по `mg_*`;
- отсутствие `mygig_*` в запросах;
- фильтры по источнику, городу, устройству, текущему статусу и специальности;
- корректную трактовку `NaT` в `first_passport_upload` и `first_ready_status`;
- расчет количества на стадии;
- расчет конверсии;
- расчет потерь без отрицательных значений в событийном режиме;
- расчет медианного времени только по валидным интервалам;
- использование правила успешной `confirmed` смены;
- shell-маршрут без тяжелого запроса;
- section-маршруты;
- рендер KPI, переходов, динамики, сегментов, узких мест и пустого состояния;
- активную навигацию и permission id;
- SQL-info для ключевых метрик.

Ручная проверка:

- `npm test`;
- открыть `/dashboards/worker-funnel`;
- проверить режим `Когорта регистраций`;
- проверить режим `События в периоде`;
- применить фильтры источника, города, устройства, статуса и специальности;
- проверить desktop viewport;
- проверить mobile viewport;
- убедиться, что PII не выводится;
- убедиться, что ошибки секций не ломают весь экран.

## Риски и ограничения

- `mg_workers.status` не является историей переходов, поэтому первая версия использует milestone-даты и явно сообщает это в SQL-info/документации.
- `first_passport_upload` и `first_ready_status` содержат строку `NaT`; ее нужно исключать при парсинге дат.
- Первая бронь считается только по `mg_job_history.status = 'booked'`. Если для части старых смен история неполная, такие брони не попадут в milestone; это консервативнее, чем считать текущий `mg_jobs.status`.
- Событийный режим не равен когортной конверсии; UI должен явно подписывать этот режим как поток событий за период.
- Большие периоды могут быть тяжелыми из-за агрегации по `mg_jobs` и `mg_job_history`. Секционная загрузка и кеш уменьшают пользовательское ожидание, но не отменяют стоимость холодного запроса.

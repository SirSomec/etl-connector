# Дизайн дашборда "Анализ городов"

Дата: 2026-06-02.

## Цель

Добавить в ETL Analytics дашборд "Анализ городов" для анализа заказа и базы исполнителей по одному выбранному населенному пункту.

Дашборд должен помогать быстро ответить на операционный вопрос: хватает ли базы исполнителей вокруг города под текущий объем заказа, как меняется этот баланс во времени и из каких брендов, профессий и ставок состоит спрос.

## Область первой версии

Нужно добавить:

- пункт меню "Анализ городов";
- маршрут `/dashboards/city-analysis`;
- обязательный выбор одного города;
- фильтры по аналогии с дашбордом "Анализ точек";
- KPI и графики для одного выбранного города;
- оценку заказа, состава заказа и базы исполнителей;
- динамику основных показателей по периодам;
- пустые состояния для случая без выбранного города или без данных.

Не входит в первую версию:

- рейтинг городов;
- карта;
- список персональных данных исполнителей;
- drill-down до карточки исполнителя;
- экспорт;
- сохраненные фильтры;
- произвольный SQL в UI.

## Основная компоновка

Используется вариант "Баланс в центре". На одном экране главный блок показывает соотношение спроса и базы исполнителей для выбранного города.

Структура страницы:

1. Заголовок "Анализ городов".
2. Компактная панель фильтров.
3. Центральный блок "Баланс спроса и базы".
4. Компактный блок динамики.
5. Компактный блок состава заказа.

На desktop все ключевые показатели должны помещаться в первый экран без необходимости прокрутки при типичной ширине рабочего монитора. На меньших экранах блоки складываются вертикально без наложения текста.

## Фильтры

Фильтры строятся по аналогии с "Анализом точек":

- диапазон дат `from/to`;
- город, обязательный одиночный выбор;
- клиент/бренд, мультивыбор;
- специальность/профессия, мультивыбор;
- тип заказа `once/regular`, мультивыбор;
- статус смены, мультивыбор;
- контрагент, мультивыбор;
- диапазон ставки `salary_per_hour`;
- флаги включения удаленных и скрытых заказов как расширенные фильтры, по аналогии с "Анализом точек".

Списки брендов, профессий, типов заказа, статусов и контрагентов зависят от выбранного периода и города. Значения фильтров передаются в ClickHouse параметрами. Множественный выбор передается как массивы ClickHouse. Пользовательский SQL не добавляется.

Если город не выбран, страница показывает фильтры и пустое состояние:

`Выберите город для анализа.`

## Источники данных

Используются таблицы `mg_*` и `appmetrica_sessions`.

Основные таблицы:

- `mg_orders` - плановый заказ и количество требуемых исполнителей;
- `mg_workplaces` - город, точки и координаты точек;
- `mg_clients` - бренд/клиент;
- `mg_professions` - профессия;
- `mg_contractors` - контрагент;
- `mg_workers` - исполнители, статусы, пользовательская связка и последняя локация;
- `mg_users` - пользовательская запись исполнителя, если нужна дополнительная связка;
- `mg_jobs` - фактические смены и завершения;
- `mg_job_history` - события бронирования/отклика;
- `appmetrica_sessions` - входы в приложение.

Основные связи:

- `mg_orders.workplace = mg_workplaces._id`;
- `mg_orders.client = mg_clients._id`;
- `mg_orders.spec = mg_professions.spec`;
- `mg_workplaces.contractor = mg_contractors._id`;
- `mg_jobs.source = mg_orders._id`;
- `mg_job_history.job = mg_jobs._id`;
- `mg_job_history.source = mg_orders._id`, если в конкретном запросе удобнее связывать историю с заказом напрямую;
- `mg_workers.user = appmetrica_sessions.profile_id`.

## Город И География

Город заказа определяется через точку заказа:

`mg_workplaces.address__city = выбранный город`.

База исполнителей определяется географически. Сначала выбираются все точки выбранного города с заполненными `location__coordinates`. Пользователь-исполнитель попадает в базу города, если его последняя локация `mg_workers.location__coordinates` находится не дальше 15 км от любой точки выбранного города.

Единица учета для базы - уникальный пользователь `mg_workers.user`. Записи `mg_workers` без заполненного `user` не участвуют в пользовательских метриках базы и активности приложения, потому что их нельзя надежно связать с `appmetrica_sessions.profile_id`.

Если в `mg_workers` будет подтверждено надежное поле города, его можно использовать как дополнительное условие включения. Основной критерий первой версии - расстояние по координатам.

Запросы по базе исполнителей должны исключать записи без координат из географического расчета. Если у города нет точек с координатами, блок базы показывает нули и пояснение, что расчет базы невозможен без координат точек.

## Временная Логика

Фильтр периода применяется к `mg_orders.start` для заказа и к датам смен/истории при расчете откликов и завершений по заказам города.

По умолчанию:

- `from` - первый день текущего месяца;
- `to` - текущая дата;
- `to` в интерфейсе включительная, в ClickHouse передается как эксклюзивная граница следующего дня.

Активность "входили в приложение за период" считается по `appmetrica_sessions.session_start_datetime` внутри выбранного периода.

Показатель "30д активные / заявка" использует фиксированное окно последних 30 календарных дней от текущей даты независимо от выбранного диапазона.

## KPI

Центральный блок "Баланс спроса и базы" показывает:

- `orderedShifts`: заказ, `sum(mg_orders.amount)` по логике "Анализа точек";
- `activeOrderRequests`: количество не удаленных заявок, `countDistinct(mg_orders._id)`;
- `totalLocatedUsers`: общая база, все пользователи-исполнители с последней локацией в радиусе 15 км от любой точки города;
- `readyLocatedUsers`: активная база, подмножество общей базы со статусом `ready`, `booked`, `worked`;
- `appActiveUsers`: пользователи-исполнители из общей базы, входившие в приложение через `appmetrica_sessions` за выбранный период;
- `bookedUsers`: уникальные пользователи-исполнители с событием `mg_job_history.status = 'booked'` по заданиям города;
- `completedUsers`: уникальные пользователи-исполнители, завершавшие задания города, по `mg_jobs.status = 'confirmed'`;
- `avgDaily30dActiveUsersPerRequest`: среднедневное отношение активных за последние 30 дней пользователей к числу не удаленных заявок.

Основной объем заказа считается как `sum(mg_orders.amount)` по не удаленным и не скрытым заявкам, если пользователь не включил соответствующие расширенные флаги. Это соответствует дашборду "Анализ точек".

`activeOrderRequests` нужен отдельно, потому что отношение "пользователей на 1 заявку" считается по количеству заявок, а не по `amount`. Для KPI `activeOrderRequests` и `avgDaily30dActiveUsersPerRequest` знаменатель всегда исключает `mg_orders.deleted = 1`, даже если расширенный фильтр включает удаленные заказы в остальных расчетах.

## Отношение 30д Активности К Заявкам

Для каждого из последних 30 дней рассчитывается:

- числитель: количество уникальных пользователей-исполнителей из географической базы города, у которых был вход в приложение в этот день;
- знаменатель: количество не удаленных заявок города на этот день;
- дневное отношение: `dailyActiveUsers / dailyActiveOrderRequests`.

Итоговый показатель:

`avgDaily30dActiveUsersPerRequest = avg(dailyActiveUsers / dailyActiveOrderRequests)` по дням, где `dailyActiveOrderRequests > 0`.

Если за последние 30 дней нет не удаленных заявок, показатель равен `0` и сопровождается нейтральной подписью.

## Состав Заказа

Состав заказа показывает топ значений внутри выбранного города и периода:

- бренды: `mg_clients.title`, объем `sum(amount)` и доля;
- профессии: `mg_professions.caption`, fallback на `mg_orders.spec`, объем `sum(amount)` и доля;
- ставки: распределение по `mg_orders.salary_per_hour`, средняя ставка и buckets.

Рекомендуемые buckets ставок для первой версии:

- `0-250`;
- `250-350`;
- `350-450`;
- `450+`.

Границы buckets задаются в коде как whitelist, а не как пользовательский SQL.

## Динамика

Динамика строится по дням для коротких диапазонов и может агрегироваться по неделям для длинных диапазонов, если это потребуется для читаемости. Периодизация выбирается из whitelist.

На графиках отображаются:

- заказ `sum(amount)`;
- входившие в приложение исполнители;
- откликавшиеся исполнители;
- завершавшие исполнители;
- отношение активных пользователей к заявкам.

В первой версии визуализация должна быть простой и устойчивой: server-rendered HTML/CSS или inline SVG без фронтенд-сборки.

## Пустые Состояния И Ошибки

Если город не выбран, показывается пустое состояние выбора города.

Если по выбранному городу нет заказов за период:

- KPI спроса равны нулю;
- графики спроса пустые;
- база исполнителей все равно считается, если у точек города есть координаты;
- отображается сообщение `Нет заказов за выбранный период.`

Если у выбранного города нет точек с координатами:

- географические показатели базы равны нулю;
- отображается сообщение `Нет координат точек для расчета базы в радиусе 15 км.`

Ошибки ClickHouse рендерятся через существующую страницу ошибки с маскированием секретов.

## Архитектура

Сохраняется текущая архитектура Express + server-rendered HTML.

Добавляется модуль `src/cityAnalysisDashboard.js`, который отвечает за:

- нормализацию фильтров;
- расчет периода и `toExclusive`;
- загрузку доступных городов и фильтров;
- безопасную сборку условий ClickHouse;
- расчет спроса;
- расчет географической базы исполнителей;
- расчет входов через `appmetrica_sessions`;
- расчет откликов и завершений;
- расчет состава заказа;
- расчет динамики;
- объединение данных в render-ready модель.

`src/server.js` добавляет маршрут `/dashboards/city-analysis`.

`src/render.js` добавляет:

- пункт навигации "Анализ городов";
- `renderCityAnalysisDashboard`;
- helpers для KPI, компактных графиков и состава заказа.

## Поток Данных

1. Пользователь открывает `/dashboards/city-analysis`.
2. Сервер нормализует query-параметры.
3. Если город не выбран, сервер загружает доступные города и рендерит пустое состояние.
4. Если город выбран, сервер загружает точки города и координаты.
5. Сервер загружает доступные значения фильтров для выбранного периода и города.
6. Сервер рассчитывает спрос по `mg_orders`.
7. Сервер рассчитывает географическую базу по `mg_workers` и точкам города.
8. Сервер рассчитывает активность приложения через `appmetrica_sessions`.
9. Сервер рассчитывает отклики через `mg_job_history`.
10. Сервер рассчитывает завершения через `mg_jobs`.
11. Сервер рассчитывает состав заказа и динамику.
12. Renderer строит один плотный экран.

## Безопасность И PII

Дашборд не выводит телефоны, email, ФИО, паспортные данные, ИНН, СНИЛС и другие персональные данные.

Все пользовательские значения передаются параметрами ClickHouse. SQL-фрагменты для периодизации, buckets ставок и сортировок берутся только из whitelist. UI не принимает произвольный SQL.

## Тестирование

Автоматические тесты должны покрыть:

- нормализацию дат и обязательного города;
- пустое состояние без выбранного города;
- передачу выбранных фильтров параметрами ClickHouse;
- whitelist для периода, buckets ставок и других SQL-фрагментов;
- расчет `orderedShifts` по `sum(amount)`;
- отдельный расчет количества не удаленных заявок;
- географическое условие 15 км от любой точки города;
- расчет общей базы как уникальных `mg_workers.user` с подходящей географией;
- разделение общей базы и активной базы `ready/booked/worked`;
- расчет входов через `appmetrica_sessions`;
- расчет откликов через `mg_job_history.status = 'booked'`;
- расчет завершавших через `mg_jobs.status = 'confirmed'`;
- расчет `avgDaily30dActiveUsersPerRequest`;
- состав заказа по брендам, профессиям и ставкам;
- рендер KPI, графиков, состава заказа и пустых состояний;
- HTML-экранирование всех отображаемых строк;
- маршрут `/dashboards/city-analysis`.

Ручная проверка после реализации:

- `npm test`;
- запуск сервера;
- открытие `/dashboards/city-analysis`;
- выбор города и проверка фильтров;
- проверка, что все обязательные показатели помещаются на один desktop-экран;
- проверка отсутствия персональных данных.

## Риски И Допущения

- Географический расчет зависит от качества `location__coordinates` у точек и исполнителей.
- Расчет "от любой точки города" может быть тяжелым для крупных городов; возможно потребуется CTE с предварительным ограничением или кэширование.
- Связка `appmetrica_sessions.profile_id = mg_workers.user` уже используется в дашборде точек, но ее качество стоит проверить на реальных данных.
- `mg_job_history` содержит много строк истории, поэтому запрос откликов должен фильтровать статус `booked` и связываться только с заказами выбранного города.
- Для длинных периодов дневные графики могут стать плотными; при необходимости первая реализация может агрегировать динамику по неделям через whitelist.

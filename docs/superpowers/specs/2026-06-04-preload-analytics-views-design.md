# Дизайн предрасчитанных витрин

Дата: 2026-06-04.

## Цель

Добавить первую итерацию предрасчитанных витрин для ускорения тяжелых дашбордов без изменения пользовательской функциональности. Пилотный дашборд - `Продажи по проектам` (`/dashboards/sales-by-project`).

После предзагрузки популярные секции дашборда должны читаться из локальной витрины и отвечать примерно за `<= 0,5 с`. Если витрина отсутствует, неполная или недоступна, дашборд сохраняет текущее поведение через fallback на ClickHouse-запросы.

## Контекст и ограничения

Сервис сейчас подключается к ClickHouse базе `etl` read-only пользователем. Возможности создавать новые таблицы или писать в ClickHouse нет, поэтому ClickHouse-витрины `analytics.*` не входят в первую итерацию.

Runtime-файлы проекта уже хранятся в `data/` и примонтированы в Docker как `./data:/app/data`. Новая витрина также хранится в этом volume. Директория должна быть доступна на запись пользователю контейнера `node`.

Произвольный SQL в UI не добавляется. Все расчеты используют заранее заданные запросы сервиса. Реальные пароли, токены и `.env` не сохраняются в репозиторий.

## Выбранный подход

Используется локальное SQLite-хранилище в текущем Node.js процессе:

- файл по умолчанию: `data/preload.sqlite`;
- env-переопределение: `PRELOAD_STORE_PATH`;
- SQLite используется как управляемое runtime-состояние деплоя и не коммитится;
- фоновые задания запускаются внутри Express-процесса;
- ручной запуск и расписание управляются через отдельную admin-страницу.

Для Node.js 22 используется встроенный `node:sqlite`, чтобы не добавлять нативные npm-зависимости и не усложнять Docker-сборку.
Так как текущий Dockerfile уже использует `node:22-bookworm-slim`, первая итерация должна поднять `package.json` engines до `>=22`. Если позднее потребуется поддержка Node.js 20 для локальной разработки, SQLite-слой нужно будет заменить на npm-библиотеку или отдельный адаптер.

## Область первой итерации

Входит:

- SQLite-хранилище `data/preload.sqlite`;
- новое право `preload-admin`;
- страница `/admin/preload`;
- настройка расписания для `sales-by-project`;
- ручной запуск обновления диапазона;
- история запусков;
- защита от параллельных запусков одного задания;
- витрина для `Продажи по проектам`;
- чтение секций `summary`, `trend`, `brands`, `statuses` из витрины;
- fallback на текущие ClickHouse-запросы при отсутствии подходящей витрины;
- документация в README и `.env.example`.

Не входит:

- перевод остальных дашбордов;
- ClickHouse-база или таблицы `analytics.*`;
- websocket/SSE live progress;
- автоматический catch-up запусков, пропущенных из-за выключенного сервера;
- синхронизация витрины между несколькими инстансами приложения;
- полный отказ от текущих ClickHouse-запросов.

## Архитектура

Новые модули:

- `src/preloadStore.js` - SQLite-хранилище, миграции, транзакционные операции, чтение статусов, расписания и витрин.
- `src/preloadSalesByProject.js` - ClickHouse-запросы предзагрузки и преобразование результата в строки витрины.
- `src/preloadScheduler.js` - запуск ручных и scheduled jobs, защита от параллельного выполнения, вычисление периода расписания.
- `src/preloadService.js` - фасад для `server.js`, UI и дашборда.

Изменяемые существующие модули:

- `src/auth.js` - добавить право `preload-admin`.
- `src/render.js` - добавить чекбокс права, страницу управления предзагрузкой и небольшую метку источника данных для `sales-by-project`.
- `src/server.js` - создать preload service, добавить маршруты `/admin/preload`, `/admin/preload/schedule`, `/admin/preload/run`, передать preload service в loader дашборда.
- `src/salesByProjectDashboard.js` - сначала читать секции из preload store при полном покрытии периода, иначе использовать текущие ClickHouse-запросы.
- `src/config.js` - добавить `PRELOAD_STORE_PATH`.
- `package.json` - поднять `engines.node` до `>=22`, потому что используется `node:sqlite`.

## Модель данных SQLite

### `preload_jobs`

Хранит настройки задания.

Ключевые поля:

- `id` - стабильный id задания, для пилота `sales-by-project`;
- `title` - пользовательское название;
- `enabled` - включено ли расписание;
- `schedule_time` - время запуска в формате `HH:mm`;
- `timezone` - для первой итерации `Europe/Moscow`;
- `refresh_days` - сколько последних дней обновлять по расписанию;
- `created_at`;
- `updated_at`;
- `last_success_at`;
- `last_run_id`.

Значения по умолчанию для `sales-by-project`:

- `enabled = 1`;
- `schedule_time = '03:00'`;
- `timezone = 'Europe/Moscow'`;
- `refresh_days = 45`.

### `preload_runs`

Хранит историю запусков.

Ключевые поля:

- `id`;
- `job_id`;
- `trigger` - `manual` или `scheduled`;
- `status` - `running`, `success`, `failed`;
- `from_date`;
- `to_date`;
- `started_at`;
- `finished_at`;
- `rows_written`;
- `error_message`.

История нужна для UI и диагностики. Ошибки должны быть очищены от секретов теми же правилами, что и ошибки ClickHouse в основном UI.

### `sales_by_project_daily`

Основная витрина пилотного дашборда.

Гранулярность: день + бренд + статусные и финансовые агрегаты, достаточные для быстрых сумм секций `summary`, `trend`, `brands`, `statuses`.

Ключевые поля:

- `period_date`;
- `brand`;
- `ordered_shifts`;
- `workplaces_with_orders`;
- `worked_shifts`;
- `revenue_rub`;
- `unique_workers`;
- `workplaces_with_worked_shifts`;
- `cancelled_shifts`;
- `self_booked_confirmed_shifts`;
- `avg_worker_rate_hour_weighted_sum`;
- `avg_worker_rate_hour_weight`;
- `status`;
- `shifts`;
- `refreshed_at`;
- `source_from`;
- `source_to`.

Индексы должны покрывать:

- диапазон дат;
- бренд;
- статус.

Для точного сохранения текущей семантики `uniqExact` и `countDistinct` по произвольным диапазонам одной дневной суммы недостаточно: сумма дневных уникальных исполнителей или точек может переучитывать одинаковые id в разные дни. Поэтому первая итерация также хранит тонкие fact-таблицы:

- `sales_by_project_order_facts` - `period_date`, `brand`, `order_id`, `workplace_id`, `ordered_shifts`;
- `sales_by_project_shift_facts` - `period_date`, `brand`, `job_id`, `worker_id`, `workplace_id`, `status`, `revenue_rub`, `cancelled_shifts`, `self_booked_confirmed_shift`, `worker_rate_hour`.

Эти таблицы используются для точных `count(DISTINCT ...)` при чтении из SQLite. Таблица `sales_by_project_daily` остается быстрым rollup-слоем для сумм, тренда и статусных счетчиков.

## Обновление витрины

Ручной запуск:

1. Пользователь на `/admin/preload` выбирает `from` и `to`.
2. Сервер валидирует диапазон дат.
3. Создается запись `preload_runs` со статусом `running`.
4. `preloadSalesByProject` выполняет заранее заданные ClickHouse-запросы за период `[from, to)`.
5. В SQLite-транзакции удаляются строки `sales_by_project_daily` за этот период.
6. Вставляются новые агрегаты.
7. Запуск помечается `success` с количеством записанных строк или `failed` с очищенным текстом ошибки.

Если ClickHouse-запрос падает до записи в SQLite, старая витрина остается нетронутой. Если ошибка возникает внутри SQLite-транзакции, транзакция откатывается.

Расписание:

1. При старте сервера `preloadScheduler` читает `preload_jobs`.
2. Если задание включено, планируется запуск на `schedule_time` в `Europe/Moscow`.
3. Запуск обновляет последние `refresh_days` календарных дней до текущей даты.
4. При изменении расписания таймер перестраивается.
5. Если сервер был выключен во время планового запуска, первая итерация не догоняет пропущенный запуск автоматически.

Параллельность:

- одновременно может выполняться только один запуск `sales-by-project`;
- повторная ручная команда во время выполнения возвращает сообщение, что обновление уже идет;
- UI не должен запускать второй пересчет того же задания.

## Чтение дашборда

`loadSalesByProjectDashboardSection` получает preload service как опциональную зависимость.

Алгоритм:

1. Нормализовать фильтры дашборда.
2. Проверить покрытие выбранного периода в `sales_by_project_daily`.
3. Если покрытие полное, построить секцию из SQLite.
4. Если покрытие неполное, SQLite недоступен или возникла ошибка чтения, использовать текущий ClickHouse loader.
5. Вернуть render model с полями `dataSource` и `preloadCoverage`.

Значения `dataSource`:

- `preload` - секция рассчитана из SQLite-витрины;
- `clickhouse` - секция рассчитана текущим ClickHouse-запросом.

UI может показывать компактную служебную метку источника данных. Метка не должна занимать место основного контента и не должна менять смысл метрик.

## Интерфейс управления

Новая страница:

```text
/admin/preload
```

Доступ требует права:

```text
preload-admin
```

В `/admin/users` появляется отдельный чекбокс `Предзагрузка витрин`. Для пользователей с ролью `admin` право выдается автоматически вместе с остальными правами.

Страница `/admin/preload` показывает:

- статус витрины `Продажи по проектам`;
- последний успешный запуск;
- покрытый период;
- признак свежести;
- последнюю ошибку;
- историю последних запусков;
- форму ручного запуска с полями `from` и `to`;
- форму расписания с полями `enabled`, `schedule_time`, `refresh_days`;
- кнопки запуска и сохранения расписания.

Маршруты:

```text
GET  /admin/preload
POST /admin/preload/schedule
POST /admin/preload/run
```

Все `POST` используют существующую CSRF-защиту.

## Безопасность

- Новые admin-маршруты закрыты правом `preload-admin`.
- Пользовательский SQL не принимается.
- Пользовательские даты валидируются и используются только как параметры заранее заданных запросов.
- Ошибки ClickHouse маскируются через существующий механизм очистки секретов.
- SQLite-файл является runtime-состоянием и не коммитится.
- Docker volume `./data:/app/data` должен быть writable для пользователя `node`.

## Риски и дальнейшие шаги

SQLite-витрина ускоряет один инстанс приложения. При нескольких репликах каждая будет иметь собственный файл `data/preload.sqlite`, если volume не общий. Для текущей первой итерации это допустимо.

Большие диапазоны ручной предзагрузки могут долго читать ClickHouse. UI должен ясно показывать статус запуска и не стартовать параллельные пересчеты.

После пилота можно добавить новые задания для `workplace-analysis`, `city-analysis`, `heatmap` и `worker-cancellations`. Для гео-дашбордов потребуется отдельная модель витрин с предрасчитанными радиусами или пространственным бакетированием.

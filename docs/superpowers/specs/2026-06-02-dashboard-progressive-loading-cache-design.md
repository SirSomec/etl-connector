# Дизайн progressive loading и кеширования дашбордов

Дата: 2026-06-02.

## Цель

Уменьшить время ожидания первого отображения текущих дашбордов ETL Analytics: там, где большие запросы можно разделить без изменения метрик, страница должна показывать каркас и фильтры сразу, а данные должны появляться по мере подгрузки независимых блоков.

Дополнительно нужно добавить новые серверные кеши на 10 часов для данных дашбордов, где кеша еще нет. Существующие кеши и их TTL не меняются.

## Область изменений

В scope входят текущие дашборды:

- `Продажи по проектам` (`/dashboards/sales-by-project`);
- `Анализ точек` (`/dashboards/workplace-analysis`);
- `Детализация точки` (`/dashboards/workplace-analysis/point`);
- `Анализ городов` (`/dashboards/city-analysis`) только в части переиспользования общей progressive-механики без изменения существующего кеша.

Не входит:

- изменение бизнес-метрик;
- изменение SQL-семантики тяжелых запросов без отдельной проверки;
- пользовательский произвольный SQL;
- frontend-сборка или SPA;
- изменение TTL существующих кешей `city-analysis` и `workplace-active-gigers`.

## Текущее состояние

`city-analysis` уже имеет progressive-загрузку через `/dashboards/city-analysis/section` и серверный кеш. Его TTL остается текущим.

`workplace-analysis` уже разбивает часть запроса на справочники, total, top workplaces, daily orders и отдельный кеш активных гигеров в радиусе 5 км. Но основной маршрут ждет весь набор данных до отдачи HTML.

`workplace-point` грузит metadata, справочники, summary, daily, professions и radius workers в одном маршруте. Радиусный блок использует `appmetrica_sessions`, `mg_workers`, координаты и может быть тяжелым.

`sales-by-project` запускает семь запросов параллельно и ждет все перед рендером. Часть запросов тяжелая из-за `mg_job_history`, `mg_transactions` и обогащения смен.

## Подход

Используется секционная серверная модель:

1. Основной маршрут дашборда загружает только данные, необходимые для формы, заголовка и пустых placeholders.
2. HTML содержит контейнеры с URL секций.
3. Небольшой встроенный JS делает `fetch` для каждой секции.
4. Секция возвращает только HTML-фрагмент без полного layout.
5. Если секция падает, страница заменяет ее placeholder на локальный блок ошибки.

Это сохраняет текущую архитектуру Express + server-rendered HTML и не добавляет клиентский state management.

## Общая progressive-механика

В `src/render.js` нужно обобщить существующий механизм `data-city-analysis-fragment-url` до общего `data-dashboard-fragment-url`.

Требования:

- старый city dashboard продолжает работать;
- фрагменты заменяются на HTML из ответа;
- фрагментная ошибка не ломает всю страницу;
- скрипт подключается только если страница содержит progressive-контейнеры;
- все строки экранируются через существующие helpers.

## Новый кеш

Добавляется общий кеш для новых секционных данных дашбордов:

- TTL: 10 часов;
- хранение в памяти и на диске;
- ключ: название дашборда, секция, нормализованные фильтры;
- защита от одновременного повторного расчета одного ключа через сохранение pending promise;
- при ошибке loader запись удаляется;
- путь по умолчанию: `data/dashboard-section-cache.json`;
- путь можно переопределить через `DASHBOARD_SECTION_CACHE_PATH`.

Существующие кеши остаются без изменения:

- `city-analysis` cache сохраняет текущий TTL;
- `workplace-active-gigers` cache сохраняет текущий TTL.

## Продажи по проектам

Основной маршрут `/dashboards/sales-by-project`:

- нормализует фильтры;
- рендерит форму и placeholders;
- не запускает семь расчетных запросов.

Новый маршрут `/dashboards/sales-by-project/section` принимает whitelist секций:

- `summary`;
- `trend`;
- `brands`;
- `statuses`.

Разбиение:

- `summary`: `orders summary` и `shifts summary`;
- `trend`: `orders trend` и `shifts trend`;
- `brands`: `brand orders` и `brand shifts`;
- `statuses`: lightweight status breakdown.

Каждая секция кешируется новым 10-часовым кешем.

## Анализ точек

Основной маршрут `/dashboards/workplace-analysis`:

- нормализует фильтры;
- загружает справочники фильтров;
- рендерит форму, контекст и placeholder списка точек;
- не ждет карточки, heatmap и активных гигеров.

Новый маршрут `/dashboards/workplace-analysis/section` принимает секцию:

- `points`.

Секция `points` выполняет текущий расчет total, top workplaces, daily rows, pinned workplaces и активных гигеров. Результат кешируется новым 10-часовым кешем. Существующий `activeGigersCache` используется внутри секции как раньше и не меняет TTL.

## Детализация точки

Основной маршрут `/dashboards/workplace-analysis/point`:

- проверяет `workplaceId`;
- загружает metadata точки и справочники фильтров;
- рендерит форму и placeholders.

Новый маршрут `/dashboards/workplace-analysis/point/section` принимает whitelist секций:

- `summary`;
- `charts`;
- `radius`.

Разбиение:

- `summary`: KPI заказа, SLA, уникальные исполнители, слеты;
- `charts`: daily rows и professions;
- `radius`: база исполнителей в радиусах 5, 10, 15, 20 км и активные за 30 дней.

Каждая секция кешируется новым 10-часовым кешем.

## Анализ городов

Существующая секционная загрузка остается. Допустимое изменение - перевести атрибуты на общий `data-dashboard-fragment-url`, сохранив совместимость и текущий кеш.

TTL кеша `city-analysis` не меняется.

## Безопасность

Пользовательские значения продолжают передаваться параметрами ClickHouse. Имена секций проверяются через whitelist. Произвольный SQL в UI не добавляется.

Дашборды не выводят PII: телефоны, email, ФИО, паспортные данные, ИНН, СНИЛС и другие персональные данные.

Ошибки ClickHouse в фрагментах проходят через существующую маскировку секрета.

## Тестирование

Автоматические тесты должны покрыть:

- основной маршрут `sales-by-project` отдает shell без тяжелых операций;
- секционный маршрут `sales-by-project/section` рендерит фрагмент и кеширует его на новом кеше;
- основной маршрут `workplace-analysis` отдает shell без загрузки карточек;
- секционный маршрут `workplace-analysis/section` рендерит список точек;
- основной маршрут `workplace-analysis/point` отдает shell после metadata и filter options;
- секционный маршрут `workplace-analysis/point/section` рендерит summary/charts/radius;
- новый кеш повторно использует данные до истечения 10 часов и перезагружает после истечения;
- ошибки секций возвращают фрагмент ошибки без полного HTML;
- общий progressive script подключается для страниц с `data-dashboard-fragment-url`;
- существующие TTL `city-analysis` и `workplace-active-gigers` не меняются.

Ручная проверка:

- `npm test`;
- запуск сервера;
- открыть все четыре дашборда;
- убедиться, что shell появляется до тяжелых блоков;
- убедиться, что блоки постепенно заменяют placeholders;
- убедиться, что поведение фильтров и расчетные подписи не изменились.

## Риски

- Для некоторых секций кеширование всего HTML-фрагмента может устаревать визуально, если позднее поменяется верстка без очистки кеша. Поэтому кеш должен хранить render-ready данные, а не HTML.
- `workplace-analysis` points section включает пагинацию; ключ кеша должен включать `limit`, `page`, pinned ids, сортировку и все фильтры.
- `workplace-point` radius зависит от текущего времени для окна активных сессий. Нормализованный фильтр уже фиксирует `activeSessionFromDateTime` и `activeSessionToDateTime`; они должны входить в ключ кеша.
- При холодном кеше тяжелые секции все равно выполняются, но пользователь уже видит shell и независимые секции могут появляться раньше.

# Дизайн самостоятельной смены пароля

Дата: 2026-06-08.

## Цель

Добавить пользователям ETL Analytics Service возможность самостоятельно менять пароль и принудительно требовать смену временного или никогда не менявшегося пароля у всех managed-пользователей.

Env-администратор из `AUTH_ADMIN_EMAIL` остается исключением: его пароль задается через `AUTH_ADMIN_PASSWORD`, не хранится в `data/users.json` и не меняется через UI.

## Контекст

Авторизация уже использует:

- env-администратора из `AUTH_ADMIN_EMAIL` / `AUTH_ADMIN_PASSWORD`;
- managed-пользователей в runtime-файле `data/users.json`;
- PBKDF2-хеши паролей;
- server-rendered Express UI;
- CSRF-токены для POST-действий.

`data/users.json` является runtime-состоянием деплоя и не коммитится. Запись уже идет через атомарный helper `writeFileAtomically`, поэтому новая смена пароля должна использовать существующее хранилище пользователей, а не отдельный файл.

## Решение

В запись managed-пользователя добавляются поля:

- `passwordChangedAt`: ISO-время последней самостоятельной смены пароля; пустое значение означает, что пользователь еще не задавал собственный пароль;
- `mustChangePassword`: `true`, если пароль временный и пользователь обязан сменить его при следующем входе.

При создании пользователя и при админском сбросе пароля `mustChangePassword` ставится в `true`, а `passwordChangedAt` очищается. Если администратор редактирует пользователя без изменения пароля, состояние пароля не меняется.

При самостоятельной смене пароля хранилище проверяет текущий пароль, качество нового пароля и отличие нового пароля от текущего. После успешной смены `mustChangePassword` становится `false`, `passwordChangedAt` получает текущее время, а `updatedAt` обновляется.

Старые записи без новых полей считаются пользователями, которые никогда не меняли пароль: публичная модель возвращает `mustChangePassword: true`.

## UI и маршруты

Добавляется страница `/account/password`, доступная любому авторизованному пользователю.

Форма содержит текущий пароль, новый пароль и подтверждение нового пароля. Страница использует существующую спокойную рабочую стилистику, без отдельного маркетингового экрана.

В верхней панели рядом с email появляется ссылка `Сменить пароль`. Она доступна для managed-пользователей. Для env-администратора ссылка не показывается, так как его пароль управляется окружением.

Если managed-пользователь имеет `mustChangePassword: true`, middleware после загрузки сессии перенаправляет все GET-запросы, кроме `/account/password`, `/logout` и служебных маршрутов, на `/account/password?required=1`. POST-запросы к другим разделам получают ошибку `403`, чтобы временный пароль нельзя было использовать для работы с данными или администрирования.

После успешной смены пароля пользователь перенаправляется на исходный локальный `returnTo` или на `/`.

## Требования к паролю

Новый пароль должен:

- содержать минимум 12 символов;
- содержать хотя бы одну строчную букву;
- содержать хотя бы одну заглавную букву;
- содержать хотя бы одну цифру;
- содержать хотя бы один спецсимвол;
- не содержать пробельные символы;
- не совпадать с текущим паролем;
- не совпадать с email пользователя или локальной частью email;
- не быть очевидным слабым значением вроде `password`, `qwerty`, `123456`, `change-me`, `admin`, `analyst`.

Те же требования применяются при создании пользователя и при админском сбросе пароля.

## Ошибки и безопасность

Ошибки формы показываются пользователю без раскрытия текущего пароля и без записи секретов в HTML вне стандартного поля ввода.

CSRF-проверка обязательна для POST `/account/password`.

Env-администратор не может менять пароль через этот маршрут. Если он откроет страницу напрямую, сервер показывает read-only объяснение, что пароль меняется через окружение.

Пароль не сохраняется в открытом виде. Для managed-пользователей сохраняется только PBKDF2-хеш.

## Тестирование

Автоматические тесты должны покрыть:

- валидацию качества пароля;
- создание пользователя с временным паролем;
- админский сброс пароля, который снова требует самостоятельную смену;
- самостоятельную смену пароля с проверкой текущего пароля;
- запрет повторного использования текущего пароля;
- совместимость старых записей без `mustChangePassword` / `passwordChangedAt`;
- принудительный редирект managed-пользователя на `/account/password`;
- исключение env-администратора из принудительной смены;
- CSRF-защиту маршрута смены пароля;
- рендер формы и HTML-экранирование.

Документация README должна описывать правила временного пароля, самостоятельную смену и требования к качеству пароля.

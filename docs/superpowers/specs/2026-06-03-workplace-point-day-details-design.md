# Дизайн детализации дня на странице точки

Дата: 2026-06-03.

## Цель

Расширить страницу `Детализация точки` в дашборде `Анализ точек`: по клику на день календаря показывать модальное окно с подробной таблицей заказов и смен за выбранный день.

Модалка должна помогать аналитику быстро понять, какие задания были запланированы в конкретный день, кто фактически завершил смены, какие были отмены и какие деньги были начислены за выполненные смены.

## Область первой версии

В первой версии нужно:

- сделать кликабельными ячейки дней в календаре точки;
- добавить отдельный endpoint деталей дня, например `/dashboards/workplace-analysis/point/details`;
- открывать модальное окно без перезагрузки страницы;
- загружать таблицу деталей через HTML-фрагмент по выбранному дню;
- передавать в запрос текущие фильтры страницы точки: `workplaceId`, диапазон, профессии, тип заказа, статусы смен, флаги удаленных и скрытых заказов;
- исключить из требований `количество откликов`;
- не добавлять пользовательский произвольный SQL.

Не входит в первую версию:

- экспорт детализации;
- редактирование заказов или смен;
- отдельный экран вместо модального окна;
- подсчет откликов;
- настройка колонок пользователем;
- справочник часовых поясов по городам.

## Рекомендованный подход

Использовать отдельный endpoint деталей по дню. Календарь остается легкой прогрессивной секцией, а тяжелые подробности грузятся только после клика пользователя.

Этот подход повторяет уже существующий паттерн дашборда `Отмены гигерами`: HTML-фрагмент деталей, модальное окно и клиентский `fetch` для подгрузки таблицы.

## Маршруты

Основная страница остается:

- `/dashboards/workplace-analysis/point`

Существующая секционная загрузка остается:

- `/dashboards/workplace-analysis/point/section?section=charts`

Новый маршрут:

- `/dashboards/workplace-analysis/point/details?workplaceId=...&date=YYYY-MM-DD`

Маршрут деталей принимает те же фильтры, что страница точки, но фактический период запроса ограничивается одним выбранным днем:

- `start >= date 00:00:00`;
- `start < date + 1 day 00:00:00`.

Если `workplaceId` пустой или `date` невалидна, endpoint возвращает HTML-фрагмент ошибки со статусом `400`. Ошибки ClickHouse проходят через существующую маскировку секретов.

## Источники данных

Используются таблицы слоя `mg_*`:

- `mg_orders` - базовый список заданий за выбранный день;
- `mg_jobs` - смены, созданные из задания через `mg_jobs.source = mg_orders._id`;
- `mg_job_history` - время перехода смены в `cancelled`;
- `mg_workers` - исполнитель смены;
- `mg_users` - ФИО и телефон исполнителя;
- `mg_professions` - человекочитаемая профессия;
- `mg_payments` - фактически начисленные или выплаченные деньги по смене.

Связи:

- `mg_orders.workplace = workplaceId`;
- `mg_orders.spec = mg_professions.spec`;
- `mg_jobs.source = mg_orders._id`;
- `mg_jobs.worker = mg_workers._id`;
- `mg_workers.user = mg_users._id`;
- `mg_job_history.job = mg_jobs._id`;
- `mg_payments.job = mg_jobs._id` или `mg_payments.entityId = mg_jobs._id`.

`mg_job_history` используется только через join к сменам выбранных заказов, а не как самостоятельная таблица периода.

## Фильтрация

Детализация дня должна уважать фильтры страницы точки:

- точка: `mg_orders.workplace`;
- выбранный день по `mg_orders.start`;
- профессия заказа;
- тип заказа `mg_orders.type`;
- статус смен через наличие связанных `mg_jobs.status`;
- флаг включения удаленных заказов;
- флаг включения скрытых заказов.

Правила фильтрации заказов должны совпадать с текущей календарной секцией, чтобы клик по дню объяснял именно те цифры, которые пользователь видит в календаре.

## Модель строк

Базовая единица детализации - задание из `mg_orders`.

Если у задания есть одна или несколько смен `mg_jobs.status IN ('confirmed', 'completed')` с ненулевым фактическим временем, таблица показывает отдельную строку на каждую такую смену. Поля задания в этих строках повторяются, потому что исполнитель, подтвержденные часы, фактическое время и начисления относятся к конкретной смене.

Если у задания нет confirmed/completed-смены с ненулевым фактическим временем, таблица показывает одну строку задания. В ней заполняются плановые поля, количество `cancelled` смен и, если отмены есть, время последнего перехода связанной смены в `cancelled`.

Такой формат сохраняет все задания дня в детализации и не прячет случаи, где план был, но факта выполнения не было.

## Колонки таблицы

Таблица содержит:

- `Профессия`;
- `Старт`;
- `План`;
- `Гигер`;
- `Телефон`;
- `Статус`;
- `Факт, ч`;
- `Факт время`;
- `Начислено`;
- `Cancelled`;
- `Последний cancelled`.

Колонки намеренно коротко названы, чтобы таблица по возможности помещалась в один экран по горизонтали.

Расшифровка:

- `Профессия` - `mg_professions.caption`, fallback на `mg_orders.spec`;
- `Старт` - старт заказа по местному времени;
- `План` - плановая длительность смены, предпочтительно `mg_orders.hours`, fallback на разницу `finish - start`;
- `Гигер` - ФИО пользователя, связанного с confirmed/completed-сменой;
- `Телефон` - `mg_users.phone` для confirmed/completed-смены;
- `Статус` - фактический статус смены: `confirmed` или `completed`, если в строке есть смена с ненулевым фактическим временем, иначе пусто;
- `Факт, ч` - подтвержденные часы смены из `mg_jobs.hours`; не рассчитывается как разница `start_fact` и `finish_fact`;
- `Факт время` - диапазон `start_fact - finish_fact`;
- `Начислено` - сумма успешных начислений по смене из `mg_payments`;
- `Cancelled` - количество связанных смен со статусом `cancelled`;
- `Последний cancelled` - время последнего события `mg_job_history.status = 'cancelled'`, только если у задания нет confirmed/completed-смены с ненулевым фактическим временем и есть cancelled-смены.

## Временная логика

День выбирается по `mg_orders.start`, как и в текущей календарной секции.

Для отображения `Старт`, `Факт время` и `Последний cancelled` первая версия использует локальное время сервиса `Europe/Moscow`. В проекте нет справочника часовых поясов по городам точки, поэтому городские часовые пояса не выводятся отдельно.

Фактическое время confirmed/completed-смены считается заполненным только если:

- `mg_jobs.status IN ('confirmed', 'completed')`;
- `start_fact` и `finish_fact` заполнены;
- `finish_fact > start_fact`.

Если фактическое время равно нулю или не может быть посчитано, такая смена не считается фактической строкой для этой таблицы.

## Начисления

`Начислено` считается по `mg_payments.amount` для платежей, связанных с confirmed/completed-сменой. Учитываются успешные статусы:

- `done`;
- `bank_done`.

Связь с платежом проверяется по `mg_payments.job = job_id` и `mg_payments.entityId = job_id`, чтобы не потерять строки при разных вариантах заполнения ETL.

Если успешных платежей нет, выводится `0`.

## UI

Ячейка календаря становится кнопкой или получает кнопку внутри себя. Визуально она остается похожей на текущую ячейку, но получает hover/focus-состояние и доступное название вида `Открыть детализацию за 2026-06-01`.

Модальное окно:

- заголовок: `Детализация дня: YYYY-MM-DD`;
- тело: таблица деталей или пустое состояние;
- закрытие по кнопке, клику на backdrop и клавише `Escape`;
- при загрузке показывает `Загружается`;
- при ошибке показывает фрагмент ошибки.

Таблица должна быть плотной:

- короткие заголовки;
- числовые значения выровнены вправо;
- даты и телефоны без переноса;
- ФИО с `text-overflow: ellipsis` на десктопе;
- минимальные внутренние отступы;
- без декоративных карточек внутри модалки.

Цель - вместить таблицу по горизонтали в обычный desktop viewport. Если ширины не хватает, используется горизонтальная прокрутка внутри таблицы, а не переносы и не расширение всей страницы.

## Безопасность и PII

Произвольный SQL не добавляется. Пользовательские значения нормализуются и передаются в ClickHouse через параметры.

Модалка намеренно выводит PII: ФИО и телефон гигера, завершившего смену. Это требуется для операционной детализации конкретного дня точки. Остальные персональные поля не выводятся.

Все значения в HTML экранируются через существующий `escapeHtml`.

## Тестирование

Автоматические тесты должны покрыть:

- нормализацию `date` для детализации дня;
- ошибку при пустом `workplaceId`;
- ошибку при невалидной дате;
- маппинг строк ClickHouse в модель детализации;
- строку confirmed/completed-смены с ФИО, телефоном, подтвержденными часами, фактическим временем и начислениями;
- строку задания без confirmed/completed, но с `cancelled` и временем последнего перехода;
- строку задания без confirmed/completed и без cancelled;
- SQL без пользовательских вставок из `workplaceId` или фильтров;
- использование `mg_orders`, `mg_jobs`, `mg_job_history`, `mg_payments`;
- новый route `/dashboards/workplace-analysis/point/details`;
- рендер HTML-фрагмента таблицы без полного layout;
- экранирование ФИО, телефона и профессии;
- наличие интерактивных календарных ячеек и `data-detail-url`;
- наличие модалки и клиентского скрипта на странице точки.

Ручная проверка:

- `npm test`;
- открыть страницу точки;
- дождаться загрузки календаря;
- кликнуть день с заказом;
- убедиться, что модалка открылась и показывает таблицу;
- проверить день без заказов или без факта выполнения;
- проверить закрытие модалки;
- проверить, что таблица на desktop помещается без переноса колонок или получает локальный горизонтальный скролл.

## Риски

- У одного заказа может быть несколько confirmed/completed-смен. Поэтому таблица показывает отдельную строку на каждую такую смену, а не пытается склеить исполнителей в одну широкую ячейку.
- `mg_payments` может хранить связь со сменой в разных полях. Запрос должен учитывать `job` и `entityId`.
- `mg_job_history` может содержать несколько событий `cancelled` на одну смену. Для времени последнего cancelled нужен `max(coalesce(createdAt, updatedAt))`.
- Длинные ФИО и телефоны могут не поместиться вместе со всеми колонками. UI должен сначала использовать компактные заголовки и ellipsis, а затем локальную горизонтальную прокрутку как fallback.
- Без справочника часовых поясов точки местное время ограничено `Europe/Moscow`.

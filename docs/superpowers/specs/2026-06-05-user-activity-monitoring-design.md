# Дизайн мониторинга активности пользователей сервиса

Дата: 2026-06-05.

## Цель

Добавить администраторский экран, на котором видно, как пользователи самого ETL Analytics Service пользуются сервисом: кто заходит регулярно, кто работает с дашбордами, кто почти не пользуется системой.

Экран должен показывать сразу несколько пользователей и давать понятную картину без перегруза цифрами и сырой аналитикой.

## Контекст

В проекте уже есть авторизация сервиса:

- env-администратор из `AUTH_ADMIN_EMAIL` / `AUTH_ADMIN_PASSWORD`;
- управляемые учетные записи в `data/users.json`;
- роли `admin` и `analyst`;
- server-rendered Express UI с админ-разделами.

Мониторинг относится только к пользователям аналитического сервиса. Он не должен смешиваться с `mg_users`, AppMetrica, сессиями мобильного приложения или другими данными MyGig.

## Решение

Использовать отдельное SQLite runtime-хранилище `data/user-activity.sqlite`.

Путь задается через `USER_ACTIVITY_STORE_PATH`, по умолчанию `./data/user-activity.sqlite`. Файл находится в `data/`, не коммитится и должен быть доступен на запись пользователю контейнера `node`, как и остальные runtime-файлы проекта.

Экран доступен по `/admin/activity` только пользователям с ролью `admin`. Отдельное permission в первой версии не добавляется. Если авторизация выключена через `AUTH_ENABLED=false`, мониторинг активности не пишет события и админ-экран активности показывает состояние “авторизация отключена” вместо пользовательской матрицы.

## События

Пишутся только серверные события, без heartbeat:

- `login` - успешный вход;
- `logout` - успешный выход;
- `page_view` - открытие полноценной HTML-страницы;
- `dashboard_filter` - открытие дашборда с измененными query-фильтрами;
- `detail_open` - открытие детализации, модального списка или drill-down endpoint;
- `export` - выгрузка данных;
- `admin_action` - успешные POST-действия в админ-разделах.

Progressive-фрагменты дашбордов не пишутся в журнал активности. Иначе один просмотр дашборда искусственно превращается в несколько действий.

## Модель Данных

Минимальная таблица событий:

```sql
CREATE TABLE user_activity_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT NOT NULL,
  email TEXT NOT NULL,
  role TEXT NOT NULL,
  event_type TEXT NOT NULL,
  method TEXT NOT NULL,
  path TEXT NOT NULL,
  section TEXT NOT NULL,
  occurred_at TEXT NOT NULL
);
```

Индексы:

```sql
CREATE INDEX idx_user_activity_events_occurred_at
  ON user_activity_events (occurred_at);

CREATE INDEX idx_user_activity_events_user_time
  ON user_activity_events (user_id, occurred_at);
```

Хранилище предоставляет методы:

- `recordEvent(event)` - записать событие;
- `pruneOldEvents(retentionDays)` - удалить события старше 90 дней;
- `getActivityOverview({ from, to })` - получить дневные уровни активности и последние действия из событий;
- `close()` - закрыть SQLite-соединение.

Сырые события старше 90 дней удаляются при записи событий и при открытии экрана мониторинга.

Экран `/admin/activity` дополнительно загружает список учетных записей из `userStore.listUsers()` и объединяет его с агрегатами событий. Поэтому в матрице видны не только активные пользователи, но и пользователи без событий за период.

## Классификация Активности

Агрегация строится по дням и пользователям.

Уровни дня:

- `none` - событий нет;
- `view` - только вход или просмотр страниц;
- `work` - фильтры, детализации, админ-действия или экспорт;
- `intense` - несколько рабочих действий за день.

Порог `intense` в первой версии задается константой в коде, например 5 рабочих событий в день. Это не бизнес-скоринг, а визуальная подсветка плотного дня.

Статус пользователя:

- `active` - есть рабочие дни за последние 14 дней;
- `rare` - активность есть, но нерегулярная;
- `silent` - нет событий за последние 30 дней;
- `new` - пользователь создан недавно и еще не накопил историю.

## UI

Главный экран `/admin/activity` - матрица пользователей:

- слева имя или email, роль и короткая метка статуса;
- в центре календарная полоска за 90 дней;
- справа “последний раз” и компактная регулярность за 30/90 дней;
- цвет ячейки дня показывает уровень активности, а не точные числа.

Сырые числа не являются главным интерфейсом. Они используются только как вторичный контекст.

По клику на пользователя раскрывается компактная детализация:

- последние действия;
- разделы, где пользователь работал;
- типы действий за выбранный период.

Сырая таблица событий не выводится как основной экран.

## Безопасность И Приватность

В события не пишутся:

- пароли;
- cookie;
- CSRF-токены;
- заголовки запроса;
- полный query string;
- значения фильтров, которые могут содержать пользовательский ввод;
- данные из ClickHouse и MyGig.

Для query-запросов хранится классификация действия и путь без чувствительных параметров. Email пользователей сервиса допустим, потому что он уже отображается в админском UI управления учетными записями.

Экран не добавляет произвольный SQL в UI и не обращается к ClickHouse.

## Ошибки

Ошибки записи активности не должны ломать основной пользовательский запрос. Если SQLite недоступна, сервер логирует ошибку и продолжает отдавать запрошенную страницу.

Если хранилище недоступно при открытии `/admin/activity`, пользователь видит стандартную error page с санитизированным сообщением без секретов.

## Тестирование

Автоматические тесты покрывают:

- инициализацию SQLite-схемы и индексов;
- запись событий;
- удаление событий старше 90 дней;
- агрегацию дневных уровней по пользователям;
- отсутствие записи для анонимных запросов и `/healthz`;
- запись `login`, `page_view`, `logout`, `admin_action`, `export`, `detail_open`;
- отсутствие завышения активности из-за progressive-фрагментов;
- доступ к `/admin/activity`: admin видит экран, analyst получает 403;
- рендер матрицы, пустого состояния и HTML-экранирование email/path.

Ручная проверка:

- `npm test`;
- локальный вход администратором;
- открытие нескольких дашбордов и фильтров;
- проверка, что `/admin/activity` показывает пользователей в матрице;
- проверка, что `data/user-activity.sqlite` создается в runtime-директории и не попадает в git.
